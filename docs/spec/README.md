# 仕様管理ガイド

このディレクトリは cfnsync の**現行仕様**と、その仕様が実装・検証されていることを追跡する索引を置く。
リリース履歴や未確定の提案をここへ混在させない。

## 文書の責務と優先順位

| 優先 | 文書 | 責務 | 含めないもの |
|---:|---|---|---|
| 1 | [requirements.md](./requirements.md) | 現在の利用者向け振る舞い、制約、安全不変条件、受入基準 | 過去仕様との比較、移行手順、実装タスク |
| 2 | [design.md](./design.md) | 要件を満たす現在の構造、データ、フロー、エラー処理 | リリース履歴、未採用案の経緯、進捗管理 |
| 3 | [traceability.md](./traceability.md) | 要件 → 設計 → 受入テスト／構造的証拠の索引 | 新しい要件、設計判断 |
| 4 | [tasks.md](./tasks.md) | T-01〜T-22 の実装記録と詳細な受入基準→テスト対応表 | 現行仕様の定義、今後の進捗管理 |

同じ事項に矛盾がある場合は上位文書を優先する。ただし、矛盾を放置してよいという意味ではない。
変更 PR 内で下位文書、テスト、利用者向け文書を上位の規範へ追随させる。

`README.md` と `docs/config-reference.md` は利用者向け説明であり、上記の規範を要約する。
[ADR](../decisions/README.md) は判断理由、[CHANGELOG](../../CHANGELOG.md) はバージョン間差分、
[変更提案](../changes/README.md) と Issue / PR は未確定または進行中の作業を扱う。いずれも現行仕様を
暗黙に上書きしない。

## 仕様変更の流れ

1. **Issue で問題を定義する**: 現在の期待を要件 ID で示し、実際の振る舞い、再現手順、影響範囲を分ける。
2. **変更提案を作る**: 複数文書・安全不変条件・互換性へ影響する変更は
   [変更提案テンプレート](../changes/template.md)で境界と選択肢を整理する。
3. **要件を先に更新する**: 外部から観測可能な振る舞いを `requirements.md` の安定 ID 付き受入基準として確定する。
4. **設計を更新する**: 各要件をどこで、どの順序・データ・防御により満たすかを `design.md` に反映する。
   長期的なトレードオフを伴う判断は [ADR テンプレート](../decisions/template.md)でも記録する。
5. **証跡を定義してから実装する**: `traceability.md` と受入テストを更新し、red → green → refactor で実装する。
6. **公開情報を同期する**: CLI、設定、運用が変わる場合は README / config reference / skills を更新する。
   利用者に見える変更や移行が必要な変更は CHANGELOG の `Unreleased` に記録する。
7. **検証する**: 影響テストと `pnpm run quality:check` を実行し、リンクと要件 ID の参照切れも確認する。

バグ修正で**規範どおりに実装を戻すだけ**なら要件本文の変更は不要である。Issue とテストで、違反していた
既存の受入基準 ID を参照する。期待する振る舞い自体を変える場合は、バグ修正という名称でも仕様変更として扱う。

## ID の安定性

- 既存の `FR-*` / `NFR-*` ID は削除後も別の意味へ再利用しない。
- 明示 ID の意味を変えず、置換が必要なら新しいサブ ID を追加して ADR / CHANGELOG に対応関係を残す。
- 明示 ID の定義は 1 基準につき 1 つとし、要件内で数値・接尾辞の順に並べる。範囲表記は参照にのみ使い、
  基準の定義ラベルには使わない。
- 旧来の箇条書き順に依存する暗黙 ID の途中へ、新しい無印の基準を挿入しない。新規基準には明示 ID を付ける。
- 1 つの受入基準は 1 つの検証可能な主張にする。複数の条件や出力契約は `a` / `b` 等のサブ ID へ分ける。
- テスト名に対応 ID を含める。自動テストにできない基準は、構造レビューまたは文書での検証方法を
  `traceability.md` に明記する。

T-22 より前の暗黙 ID とその詳細対応は [tasks.md](./tasks.md) に保存する。既存 ID の一括再採番は行わず、
変更対象に触れる際に上記規約へ段階的に寄せる。

`pnpm run check:docs` は規範 SoT の節番号、`FR-1`〜`FR-13` / `NFR-1`〜`NFR-6` の見出し連番、
明示 ID の単一定義・重複・並び順を検査する。新しい ID 規約は品質ゲートで退行を防止する。

## 安全不変条件の変更

fail-closed、ステート CAS、ロックと fencing、変更セット所有権、`REVIEW_IN_PROGRESS` の保護、管理タグ、
削除順序に関わる変更は通常の仕様変更より高リスクである。変更提案には少なくとも次を含める。

- 影響する FR / NFR と現在の失敗モード
- 保護を弱めないことを示す異常系・並行系の受入基準
- AWS 副作用より前に停止する境界と、残る TOCTOU 競合窓
- 障害復旧、ロールバック、移行手順
- 敵対的レビューの結果と未解決リスク

安全不変条件を「警告して継続」へ緩和する変更は、明示的な要件変更・ADR・移行記録なしに行ってはならない。
