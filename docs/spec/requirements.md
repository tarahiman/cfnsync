# cfnsync 要件定義書

## 1. 概要

cfnsync は、ディレクトリ内の CloudFormation テンプレートファイルの追加・更新・削除をトリガーに、対応する CloudFormation スタックを自動で作成・更新・削除する CLI ツールである。

## 2. 背景・目的

- 新規にインフラを構築する場合は CDK や Terraform を使用すればよいが、過去に生の CloudFormation で構築され、そのまま運用されているプロダクトが存在する。本ツールはそうしたプロダクトの IaC 運用を楽にすることを目的とする。
- あくまで生の CloudFormation の運用をサポートするツールであり、CDK のような新たな IaC ツール(抽象化レイヤーやテンプレート生成機構)を生み出すことは目的ではない。
- CI/CD への組み込みを前提とし、必要最低限の機能に絞る。
- 将来的に GitHub Actions 上での実行を見据える。

## 3. スコープ

### 3.1 スコープ内

- ローカルディレクトリ内の CloudFormation テンプレート(YAML / JSON)の変更検知
- 変更セット(Change Set)の作成・差分表示・実行によるスタックのライフサイクル管理(作成・更新・削除)
- テンプレート間の依存関係の解析と、依存順序に従ったデプロイ
- CI/CD(特に GitHub Actions)から非対話で実行できる CLI インターフェース

### 3.2 スコープ外

- テンプレートの生成・抽象化(CDK / SAM のようなトランスパイル機構)
- テンプレートの Lint・静的解析(cfn-lint 等の既存ツールに委ねる)
- スタックのドリフト検出・修復
- 複数 AWS アカウントへの一括デプロイ(StackSets 相当の機能)
- GUI / Web UI

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| テンプレート | 管理対象ディレクトリ内の CloudFormation テンプレートファイル |
| スタック | テンプレートに対応する CloudFormation スタック |
| ステート | 前回デプロイ成功時点(またはインポートで実環境と検証した時点)のテンプレート群の状態を記録したデータ。変更検知の基準となる |
| 変更セット | CloudFormation Change Set。適用前に差分を確認できる仕組み |
| 依存関係 | あるスタックの Export を別のスタックが `Fn::ImportValue` で参照する等、デプロイ順序に制約を生む関係 |

## 5. 機能要件

各要件には TDD の受け入れテストの基準となる受け入れ基準(EARS 形式)を付す。

### FR-1: 変更検知とステート管理

管理対象ディレクトリ内のテンプレートファイルについて、前回デプロイ時点からの「追加・変更・削除」を判別できること。

- WHEN 変更検知を実行した場合、ツールはステートと現在のファイル群を比較し、各テンプレートを `added` / `modified` / `deleted` / `unchanged` のいずれかに分類しなければならない。
- ファイルの比較はコンテンツのハッシュに基づいて行い、タイムスタンプのみの変更は「変更なし」と判定しなければならない。
- WHEN デプロイ(または削除)が成功した場合、ツールは該当テンプレートのステートを更新しなければならない。デプロイが失敗したテンプレートのステートは更新してはならない。
- ステートはバックエンドに保存する。バックエンドとして少なくとも `local`(ローカルファイル)と `s3`(S3 オブジェクト)を選択できなければならない(Terraform のステート管理と同様の方式)。
- `local` バックエンドは単一環境での利用を想定する。複数の実行環境(CI ランナー等)から利用する場合は `s3` バックエンドを使用しなければならないことをドキュメントに明記する。
- ステートは世代(バージョン)情報を持たなければならない。WHEN ステートを保存する場合、ツールは読み込み時点から他者によって変更されていないことを検証し、変更を検出した場合は上書きせずエラーとしなければならない(compare-and-swap)。`s3` バックエンドでは S3 の条件付き書き込みによってこれを保証する。
- WHEN 変更系操作を開始する場合、`s3` バックエンドではステートに対するロックを取得しなければならない。IF ロックを取得できない(他の実行が保持している)場合、ツールは一切の変更を行わずエラーで終了しなければならない。ロックは正常・異常を問わず実行終了時に解放し、残存したロックを手動で解除する手段を提供しなければならない。
- ロックの解放(手動解除を含む)は、解放対象が自身の(または指定された)ロックであることを検証する条件付き操作で行わなければならない。
- ツールは各副作用(AWS への変更操作・ステート保存・ローカルファイルの書き込み)の直前にロックの所有権を検証し、WHEN 所有権を失っていた場合、当該副作用以降の処理を行わず中断しなければならない(fencing)。この検証は検証と副作用の間の競合窓を完全には排除できないベストエフォートであることを仕様上明記し、正本の一貫性はステート保存の compare-and-swap(競合した側の保存は必ず失敗する)およびスタック単位の進行中操作ガード(FR-2)によって保証しなければならない。
- ロックの手動解除は、保持していた実行が終了していることを利用者が確認した場合にのみ行う操作として位置づけ、ツールは実行時にロックの内容(実行 ID・開始時刻・実行者)と警告を表示しなければならない。手動解除後の再実行では、変更検知と変更セットの再作成によってステートと実環境の乖離が解消されること(冪等復旧)。
- WHEN AWS 操作は成功したがステート保存に失敗した場合(fencing 中断・CAS 競合・クラッシュ等)、次回実行は実スタックとの突合により自動で収束しなければならない: (a) IF `added` 分類のスタックキーに同名スタックが既に存在する場合、実スタックから検証可能な入力のすべて — 正規化したテンプレート(パース後の同値比較)、実効パラメータ、タグ、Capabilities — が希望する内容と一致する場合のみ、デプロイ成功として再同期しなければならない。一致条件には、ツールが自動付与する管理タグ(FR-2)により当該スタックが自ステートの実行によって作成されたことの確認(由来確認)を含めなければならない。IF 管理タグによる由来確認ができない(欠如または不一致の)場合、他の入力がすべて一致しても再同期してはならない(fail-closed)。実スタックから同値性を検証できない入力(明示依存、NoEcho パラメータの実値)は一致条件に含めず、再同期時にローカルの希望値として記録する。一つでも不一致がある場合は命名衝突または管理外スタックの可能性としてエラーとし、インポート(FR-10)を案内しなければならない。(b) IF `deleted` 分類のスタックが存在しない場合、削除成功としてステートから除去しなければならない。(c) 更新(UPDATE)は空変更セット(FR-2)により再同期されること。
- ステートの保存は原子的に行わなければならない。IF ステートの破損(不完全な書き込み等)を検出した場合、ツールは変更系操作を拒否しなければならない(fail-closed)。
- ステートは単一の AWS アカウントに紐付けなければならない。WHEN 変更系操作を行う場合、ツールは接続先アカウント(FR-7)とステートに記録されたアカウント ID の一致を検証し、不一致の場合は実行を拒否しなければならない。複数アカウントを扱う場合は設定・ステートの組を分離する。
- WHEN スタック名の設定が変更された場合、ツールはこれを「旧スタック名のスタックの削除 + 新スタック名のスタックの新規作成」として扱わなければならない。削除は FR-6 の安全装置に従う。
- IF ステートが存在しない(初回実行)場合、ツールは全テンプレートを `added` として扱うか、既存スタックとの初期同期(FR-10)を促さなければならない。

### FR-2: 変更セットの作成

変更されたテンプレートに対して CloudFormation 変更セットを作成できること。

- WHEN `modified` のテンプレートに対して変更セット作成を実行した場合、ツールは対象スタックに `UPDATE` タイプの変更セットを作成しなければならない。
- WHEN `added` のテンプレートに対して変更セット作成を実行した場合、ツールは `CREATE` タイプの変更セットを作成しなければならない。
- IF 変更セットの Status が `FAILED` で、StatusReason を前後空白の除去により正規化した値が AWS の既知の「変更なし」定型文(`The submitted information didn't contain changes. Submit different information to create a change set.` / `No updates are to be performed.`)のいずれかに**完全一致**し、かつ `Changes` が空の場合に限り、ツールはこれをエラーではなく「変更なし」として扱い、後続処理をスキップしなければならない。既知文面に suffix が付く場合や、`Changes` が空でも別理由の場合を含む、それ以外の `FAILED` はエラーとして扱わなければならない。
- IF 対象スタックが `ROLLBACK_COMPLETE` 等のデプロイ不能ステータスの場合、ツールは明確なエラーメッセージと対処方法(スタック削除の必要性など)を提示しなければならない。
- テンプレートに IAM リソース等が含まれる場合に必要な Capability(`CAPABILITY_IAM` / `CAPABILITY_NAMED_IAM` / `CAPABILITY_AUTO_EXPAND`)を設定ファイルまたは CLI オプションで指定できなければならない。
- ツールが作成する変更セットは `cfnsync-<stateId:12hex>-<runId:16hex>-<UTC:YYYYMMDDTHHmmssSSS>` に完全一致しなければならない。残存変更セットはこの形式に完全一致する場合だけ所有権を判定し、形式不一致は判定不能として fail-closed に中断しなければならない。
- WHEN 対象スタックにツールが過去に作成した未実行の変更セットが残存する場合(dry-run の残骸や失敗した前回実行を含む)、ツールはそれを検出し、破棄した上で新たな変更セットを作成しなければならない。回収対象は、ツール自身が作成し、かつ自身と同一のステートに紐づくと検証できた変更セットに限り、他のツール・人手による変更セットに触れてはならない。IF 所有権を検証できない、または別のステート設定に紐づくツール由来の変更セットを検出した場合、ツールは変更セットを破棄せず中断しなければならない。この残存回収は**対象スタックが CloudFormation に既に存在する場合に限り**適用する。IF 対象スタックが CloudFormation に一切存在しない(真の新規 `CREATE`)場合、ツールは残存変更セットの列挙(`ListChangeSets`)を行わず、直接変更セットを作成しなければならない(存在しないスタックへの `ListChangeSets` は AWS 側のエラーとなるため)。
- IF 対象スタックが他の操作により `*_IN_PROGRESS` 状態にある場合、ツールは変更セットを作成せず、並行操作の存在をエラーとして報告しなければならない。
- ツールは、作成・更新するスタックに管理主体を識別するタグ(ステートの識別子を含む)を自動付与しなければならない。このタグは復旧時の同一性判定(FR-1)における由来(provenance)の確認に用いる。
- ツールは、変更セット未実行のまま残された空スタック(`REVIEW_IN_PROGRESS`)に対して、スタック自体の削除を行ってはならない。ツールは自身の所有と検証できた変更セットのみを個別に破棄し、新規作成型の変更セットを当該スタック上に再作成して続行しなければならない。IF 他主体の変更セットが存在する場合、変更セットを作成せずエラーとして停止しなければならない(fail-closed)。
- WHEN 変更セットを作成した場合、ツールは `CreateChangeSet` が返した変更セット ARN を保持し、待機・詳細取得・実行直前再検査・実行をその ARN で行わなければならない。WHEN 変更セットを実行する場合、ツールは実行の直前に対象スタックの未実行変更セットを再検査し、自身が作成した名前と ARN の双方が一致することを検証しなければならない。IF 自変更セットが欠落・差し替えされている、または他主体(ツール以外または別ステート)の変更セットが存在する場合、実行せずエラーとして停止しなければならない(CloudFormation の変更セット実行は同一スタックの他の変更セットを暗黙に削除するため)。再検査から実行までの競合窓は原理的に排除できないことを仕様に明記し、管理対象スタックに手動の変更セットを作成しない運用をドキュメントで求めなければならない。

### FR-3: 変更セットの差分表示

作成された変更セットの内容を人間が確認できる形式で出力できること。

- 変更セットに含まれるリソース単位の変更(Add / Modify / Remove)と、変更対象のプロパティを表示しなければならない。
- IF リソースの置換(Replacement)が発生する変更が含まれる場合、ツールはそれを明確に警告として強調表示しなければならない。
- 出力形式として人間可読なテキストに加え、機械可読な JSON を選択できなければならない(GitHub Actions での PR コメント生成等に利用するため)。

### FR-4: 変更セットの実行(デプロイ)

作成済みの変更セットを実行し、デプロイを行えること。

- WHEN 変更セットを実行した場合、ツールはスタック操作の完了(成功または失敗)まで待機し、スタックイベントを逐次出力しなければならない。
- IF デプロイが失敗した場合、ツールは失敗の原因となったリソースとエラーメッセージを出力し、非ゼロの終了コードで終了しなければならない。
- IF デプロイ失敗によりロールバックが発生した場合、ツールはロールバックの発生と結果を報告しなければならない。

### FR-5: 変更セット作成とデプロイの一括実行

変更セットの作成から実行までを 1 コマンドで行えること。

- WHEN 一括実行コマンドを実行した場合、ツールは変更検知 → 依存順序の解決 → 変更セット作成 → 差分表示 → 実行を一連で行わなければならない。
- 一括実行はデフォルトで非対話(確認プロンプトなし)で完走しなければならない(CI 前提)。ローカル利用向けに、実行前に確認を求めるオプションを提供してもよい。
- `--dry-run` オプションにより、変更セットの作成と差分表示までで停止(実行しない)できなければならない。

### FR-6: スタックの削除

テンプレートファイルの削除をトリガーに、対応するスタックを削除できること。

- WHEN `deleted` と判定されたテンプレートが存在する場合、ツールは対応するスタックを削除対象として差分表示に含めなければならない。
- スタックの削除は、明示的なオプション(例: `--allow-delete`)が指定された場合にのみ実行しなければならない。デフォルトでは削除対象の存在を警告として報告し、削除は行わない(安全側に倒す)。
- IF スタックに削除保護(Termination Protection)が有効な場合、ツールは保護を自動解除せず、エラーとして報告しなければならない。
- 削除順序は、現在のテンプレート群から構築した依存関係グラフに加え、ステートに保存された前回成功時点のグラフ(FR-8。削除対象スタックが保持していた依存辺を含む)を統合して決定し、依存の逆順で実行しなければならない。
- IF 削除対象スタックの依存情報がステートから復元できない、または曖昧な場合、ツールは当該スタックの削除を拒否し、手動対応が必要であることを報告しなければならない。
- スタック削除は FR-7 の接続先検証(fail-closed)の対象であり、`--allow-delete` は接続先検証を通過した場合にのみ有効である。

### FR-7: 認証・接続設定

AWS への認証は標準的な方法で行えること。

- `~/.aws/config` のプロファイルを CLI オプション(例: `--profile`)または環境変数 `AWS_PROFILE` で指定して認証できなければならない。
- プロファイル未指定の場合は AWS SDK の標準クレデンシャルチェーン(環境変数 → プロファイル → IAM ロール等)に従わなければならない。これにより GitHub Actions の OIDC(`aws-actions/configure-aws-credentials`)で払い出された一時クレデンシャルがそのまま利用できること。
- リージョンを CLI オプション・環境変数・設定ファイルのいずれかで指定できなければならない。
- ツール自身がクレデンシャルを独自に保存してはならない。

誤接続防止(接続先検証):

- 設定ファイルで、操作を許可する AWS アカウント ID および許可するリージョン(複数指定可)を指定しなければならない。この設定はすべての変更系操作の前提条件である。
- WHEN 変更系操作(変更セットの作成・実行・スタック削除)を行う場合、ツールは STS `GetCallerIdentity` により接続先アカウントを解決し、許可設定と照合しなければならない。IF 許可設定が未設定・不一致・解決不能のいずれかの場合、ツールは変更セットの作成を含む一切の変更系操作を行わず、エラーで終了しなければならない(fail-closed)。
- 読み取り専用操作(status / graph / import 等)は許可設定なしでも実行してよい。ただし解決した接続先を出力に含めなければならない。IF 操作がステートへの書き込みを伴う場合(import)、FR-1 のアカウント照合とロック取得を行わなければならない。
- 解決した接続先(アカウント ID・リージョン)を実行ログおよび JSON 出力に含めなければならない(クレデンシャル等の秘匿情報は含めない)。

### FR-8: 依存関係マッピングの出力

テンプレート間の依存関係を解析し、マッピングとして出力できること。

- ツールはテンプレートの `Export`(Outputs)と `Fn::ImportValue` を解析し、スタック間の依存関係グラフを構築しなければならない。
- 自動解析で表現できない依存関係(パラメータ経由の参照等)のために、設定ファイルで明示的に依存関係を宣言できなければならない。
- 依存関係マッピングを人間可読な形式(テキストツリー等)および機械可読な形式(JSON)で出力できなければならない。
- IF 依存関係に循環が存在する場合、ツールは循環に含まれるスタックを明示してエラーとしなければならない。
- WHEN デプロイまたは削除が成功した場合、ツールはその時点の依存関係グラフ(または再構築に必要な Export / Import 情報)をステートに保存しなければならない。テンプレートファイルが削除された後でも、そのスタックが保持していた依存辺を参照できるようにするためである(→ FR-6)。

### FR-9: 依存順序に従ったデプロイ

デプロイは依存関係マッピングのトポロジカル順序に従って実行されること。

- WHEN 複数のスタックがデプロイ対象の場合、ツールは依存されるスタックを先に、依存するスタックを後にデプロイしなければならない。
- IF あるスタックのデプロイが失敗した場合、そのスタックに依存する後続スタックのデプロイは中止し、依存関係のない他のスタックの扱い(継続 or 全体中止)はオプションで選択できなければならない。
- 相互に依存のないスタックの並列デプロイは将来拡張とし、初期リリースでは直列実行でよい(設計上は並列化を妨げない構造とする)。

### FR-10: 既存スタックのインポート(初期同期)

既存運用中のプロダクトを対象とするため、すでにデプロイ済みのスタックを再作成せずに管理下に置けること。インポートは実環境を正として行い、実環境とローカルの差異を隠蔽してはならない。

- WHEN インポートを実行した場合、ツールは既存スタックから以下を取得し、ローカルの設定ファイル(FR-11)に反映しなければならない: スタック名、現在のパラメータ値、タグ、必要な Capabilities。
- IF パラメータが `NoEcho` の場合、実値は取得できないため、設定ファイルには要入力を示すプレースホルダを記録しなければならない。マスク値(`****`)をそのまま実値として書き込んではならない。
- WHEN インポートを実行した場合、ツールはデプロイ済みテンプレート(`GetTemplate`)とローカルのテンプレートファイルを比較しなければならない。
- IF デプロイ済みテンプレートとローカルテンプレートに差分がある場合、デフォルトではエラーとし、明示的なオプションにより以下のいずれかを選択できなければならない: (a) デプロイ済みテンプレートでローカルファイルを上書きする、(b) 差分を承知の上でローカルファイルを維持し、その差分が次回の plan で変更として顕在化するようにステートを記録する。
- IF ローカルにテンプレートファイルが存在しないスタックを取り込む場合、ツールはデプロイ済みテンプレートをローカルファイルとして書き出せなければならない。
- ステートには検証済みの対応関係と、デプロイ済みテンプレートの内容に基づくハッシュを記録しなければならない。未デプロイのローカル内容を「デプロイ済み」としてステートに記録してはならない。
- インポートは AWS に対して読み取り専用でなければならない。書き込み対象はローカルの設定ファイル・ステート・テンプレートファイルのみとする。
- WHEN インポートを実行した場合、ツールは STS により接続先アカウントを解決し、ステートに記録されたアカウント ID と照合しなければならない(FR-1)。照合はロック取得後に再読込したステートに対して行い、ロック取得前に読んだステートを判断に使用してはならない。IF 不一致の場合、設定ファイル・ステート・テンプレートファイルへの一切の書き込みを行わずエラーで終了しなければならない。IF ステートが未作成(初回)の場合、解決したアカウント ID をステートの作成と同一ロック区間内の保存操作(compare-and-swap)で記録しなければならない。
- インポートはステートを書き込むため、ロックの取得(FR-1)を変更系操作と同様に行わなければならない。
- IF テンプレートに対応するスタックが存在しない場合、そのテンプレートは `added`(新規作成対象)として扱わなければならない。

### FR-11: 設定ファイル

テンプレートとスタックの対応やデプロイパラメータを設定ファイルで管理できること。

- テンプレートファイルごとに以下を設定できなければならない: スタック名、デプロイ先リージョン(複数可、FR-13)、パラメータ(またはパラメータファイルへの参照)、タグ、Capabilities、明示的な依存関係、リージョンごとのパラメータ・タグの上書き。
- 全体設定として、ステートバックエンド(`local` / `s3` とその接続情報)を設定できなければならない(FR-1)。
- スタック名が未設定の場合の規約(例: ファイル名からの導出)を持ち、設定を最小限で運用できなければならない。
- 設定ファイルはリポジトリにコミット可能なテキスト形式(YAML 等)でなければならない。
- 設定ファイルに不備がある場合(存在しないテンプレートへの参照、必須項目欠落等)、ツールは実行前の検証で検出し、具体的なエラーを報告しなければならない。
- `stacks` のキーであるテンプレートパスは設定ファイルのディレクトリを基準とする相対パスに限り、絶対パス・NUL を含むパス・正規化後に `..` から始まるパスを設定検証時に対象キーを示す `ConfigError` で拒否しなければならない。サブディレクトリを含む正当な相対パスは許可する。
- WHEN テンプレートを読み取りまたは import で書き込む場合、解決先の実パス(未作成なら既存の最長親ディレクトリの realpath から解決したパス)が設定ファイルのディレクトリ配下であることを検証しなければならない。IF シンボリックリンク等を経由して範囲外へ到達する場合、一切のローカル書き込みを行わずエラーで終了しなければならない。

### FR-12: CLI インターフェース

- ツールは少なくとも以下に相当するサブコマンドを提供しなければならない:
  - 変更検知結果の表示(status 相当)
  - 変更セット作成+差分表示(plan / diff 相当)
  - デプロイ実行(deploy / apply 相当)
  - 依存関係マッピング表示(graph 相当)
  - 既存スタックのインポート(import 相当)
- 終了コードは CI で判定可能なように定義しなければならない(例: 0 = 成功/変更なし、1 = 実行エラー、2 = 差分あり(dry-run 時)等)。
- すべてのコマンドは TTY なしの環境(CI)で動作しなければならない。

### FR-13: マルチリージョンデプロイ

1 つのテンプレートを複数のリージョンへデプロイできること。

- 設定ファイルで、テンプレートごとにデプロイ先リージョンを複数指定できなければならない。未指定の場合は既定リージョン 1 つへのデプロイとする。
- リージョンごとのスタックは独立したスタックとして扱い、変更検知・ステート・変更セット・差分表示は(テンプレート × リージョン)単位で管理しなければならない。
- パラメータおよびタグは、共通値に対してリージョンごとの上書きを指定できなければならない(AMI ID や証明書 ARN などリージョン依存の値に対応するため)。
- WHEN テンプレートが変更された場合、ツールは設定されたすべての対象リージョンに対して変更セットを作成しなければならない。
- WHEN 設定に対象リージョンが追加された場合、当該リージョンのスタックを `added`(新規作成対象)として扱わなければならない。WHEN 設定から対象リージョンが削除された場合、当該リージョンのスタックを削除対象として扱い、FR-6 の安全装置に従わなければならない。
- 依存関係グラフ(FR-8)はリージョンごとに独立して構築・評価しなければならない(CloudFormation の Export / ImportValue は同一リージョン内でのみ参照可能なため)。リージョン内のデプロイ順序は FR-9 に従い、リージョン間の実行順は設定順の直列とする(並列化は将来拡張)。
- 差分表示・実行ログ・JSON 出力には対象リージョンを明示しなければならない。
- 対象リージョンは FR-7 の許可リージョン設定に含まれていなければならない。IF 含まれないリージョンが指定された場合、fail-closed でエラーとしなければならない。
- インポート(FR-10)はリージョンごとに実行でき、既存のリージョン別スタックを取り込めなければならない。

## 6. 非機能要件

### NFR-1: CI/CD 適合性

- 非対話で完結し、進捗・結果を標準出力/標準エラーに構造的に出力すること。
- GitHub Actions からの利用を想定し、差分の JSON 出力・終了コードによる判定・ログの見やすさを備えること。

### NFR-2: テスト容易性(TDD 前提)

- AWS API 呼び出しはインターフェースとして抽象化し、モック/スタブによる単体テストが可能な構造とすること。
- 変更検知・依存解析・順序解決などのコアロジックは AWS 接続なしでテストできること。

### NFR-3: 信頼性・冪等性

- 同一状態に対する再実行は安全であること(冪等)。途中失敗後の再実行で、成功済みスタックはスキップまたは「変更なし」となり、失敗地点から継続できること。再実行時には前回実行が残した変更セットを FR-2 に従い検出・回収できること。
- 同一スタックに対する並行操作を検出した場合(`*_IN_PROGRESS` ステータス、ステート世代の不一致)、状態を破壊せず安全に失敗すること。
- `s3` バックエンドのロックと条件付き書き込み(FR-1)により、CI の直列化設定が漏れて並行実行が発生した場合でも、後発の実行はロック取得に失敗して安全に停止し、ステートの正本が破損しないこと。CI 側の直列化(例: GitHub Actions の `concurrency` グループ)は、ロック競合による失敗を待機に変えるための推奨構成としてドキュメント化すること。
- AWS API のスロットリングに対してリトライ(指数バックオフ)を行うこと。

### NFR-4: セキュリティ

- クレデンシャルを保存・出力しないこと。
- `NoEcho` パラメータ等の秘匿値をログ・差分出力・JSON にマスクして表示すること。対象スタックの設定上の実効パラメータから得た NoEcho 実値を usecase 境界の共通 redactor で `****` に置換し、スタックイベントの `ResourceStatusReason`、スタック/変更セットの `StatusReason`、AWS 例外メッセージ、最終 `errorMessage` を report に格納または逐次通知する前に必ず通すこと。空文字および 4 文字未満の値は誤マスク防止のため置換対象外とする。
- ツールの実行に必要な最低限の IAM 権限をドキュメント化すること。

### NFR-5: パフォーマンス

- 数十テンプレート規模のディレクトリで実用的な時間で動作すること。status / graph の変更検知・グラフ構築は CloudFormation / STS API を呼ばずローカルで完結すること。ただし、status で S3 state backend のステートを読み取る API 呼び出しは除く。
- 変更セット待機は先頭ページの状態だけをポーリングし、終端到達時にのみ全ページの差分を取得すること。スタック待機はイベントを 5 秒間隔で取得し、スタック状態取得は 5 秒から最大 15 秒までバックオフすること。

### NFR-6: 保守性

- 機能追加(並列デプロイ、S3 ステートバックエンド、GitHub Actions パッケージング)を想定したモジュール構成とすること。

## 7. 制約条件

- 対象は生の CloudFormation テンプレート(YAML / JSON)とする。テンプレートの変換・生成は行わない。
- CloudFormation がネイティブにサポートする範囲の機能のみを利用する(独自のプロビジョニングロジックを持たない)。
- 1 テンプレートファイル = 1 スタック(リージョンごと)の対応を基本とする。1 つのテンプレートを複数リージョンにデプロイする場合、リージョンごとに独立したスタックとして扱う(FR-13)。

## 8. 将来的な拡張(初期リリースのスコープ外)

- GitHub Actions アクションとしてのパッケージング(差分の PR コメント投稿を含む)
- 独立したスタックの並列デプロイ
- ネスト済みスタック・テンプレートの S3 アップロード対応
