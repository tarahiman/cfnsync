# cfnsync 要件定義書

> **規範 SoT:** 本書は現在の外部仕様と安全上の制約を定義する。過去仕様との差分・移行手順は
> [CHANGELOG](../../CHANGELOG.md)、判断理由は [ADR](../decisions/README.md)、実装・テストへの対応は
> [トレーサビリティ](./traceability.md)を参照する。更新規則は[仕様管理ガイド](./README.md)に従う。

## 1. 概要

cfnsync は、ディレクトリ内の CloudFormation テンプレートファイルの追加・更新・削除をトリガーに、対応する CloudFormation スタックを自動で作成・更新・削除する CLI ツールである。

## 2. 背景・目的

- 新規にインフラを構築する場合は CDK や Terraform を使用すればよいが、過去に生の CloudFormation で構築され、そのまま運用されているプロダクトが存在する。本ツールはそうしたプロダクトの IaC 運用を楽にすることを目的とする。
- あくまで生の CloudFormation の運用をサポートするツールであり、CDK のような新たな IaC ツール(抽象化レイヤーやテンプレート生成機構)を生み出すことは目的ではない。
- CI/CD への組み込みを前提とし、必要最低限の機能に絞る。
- 将来的に GitHub Actions 上での実行を見据える。

## 3. スコープ

### 3.1 スコープ内

- ローカルディレクトリ内の CloudFormation テンプレート(YAML / JSON)の変更検知
- 変更セット(Change Set)の作成・差分表示・実行によるスタックのライフサイクル管理(作成・更新・削除)
- テンプレート間の依存関係の解析と、依存順序に従ったデプロイ
- CI/CD(特に GitHub Actions)から `--auto-approve` により非対話で実行できる CLI インターフェース

### 3.2 スコープ外

- テンプレートの生成・抽象化(CDK / SAM のようなトランスパイル機構)
- テンプレートの Lint・静的解析(cfn-lint 等の既存ツールに委ねる)
- スタックのドリフト検出・修復
- 複数 AWS アカウントへの一括デプロイ(StackSets 相当の機能)
- GUI / Web UI

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| テンプレート | 管理対象ディレクトリ内の CloudFormation テンプレートファイル |
| スタック | テンプレートに対応する CloudFormation スタック |
| ステート | 前回デプロイ成功時点(またはインポートで実環境と検証した時点)のテンプレート群の状態を記録したデータ。変更検知の基準となる |
| 変更セット | CloudFormation Change Set。適用前に差分を確認できる仕組み |
| 依存関係 | あるスタックの Export を別のスタックが `Fn::ImportValue` で参照する等、デプロイ順序に制約を生む関係 |

## 5. 機能要件

各要件には TDD の受け入れテストの基準となる受け入れ基準(EARS 形式)を付す。

### FR-1: 変更検知とステート管理

管理対象ディレクトリ内のテンプレートファイルについて、前回デプロイ時点からの「追加・変更・削除」を判別できること。

- WHEN 変更検知を実行した場合、ツールはステートと現在のファイル群を比較し、各テンプレートを `added` / `modified` / `deleted` / `unchanged` のいずれかに分類しなければならない。
- ファイルの比較はコンテンツのハッシュに基づいて行い、タイムスタンプのみの変更は「変更なし」と判定しなければならない。
- WHEN デプロイ(または削除)が成功した場合、ツールは該当テンプレートのステートを更新しなければならない。デプロイが失敗したテンプレートのステートは更新してはならない。
- ステートはバックエンドに保存する。バックエンドとして少なくとも `local`(ローカルファイル)と `s3`(S3 オブジェクト)を選択できなければならない(Terraform のステート管理と同様の方式)。
- `local` バックエンドは単一環境での利用を想定する。複数の実行環境(CI ランナー等)から利用する場合は `s3` バックエンドを使用しなければならないことをドキュメントに明記する。
- ステートは世代(バージョン)情報を持たなければならない。WHEN ステートを保存する場合、ツールは読み込み時点から他者によって変更されていないことを検証し、変更を検出した場合は上書きせずエラーとしなければならない(compare-and-swap)。`s3` バックエンドでは S3 の条件付き書き込みによってこれを保証する。
- WHEN 変更系操作を開始する場合、`s3` バックエンドではステートに対するロックを取得しなければならない。IF ロックを取得できない(他の実行が保持している)場合、ツールは一切の変更を行わずエラーで終了しなければならない。ロックは正常・異常を問わず実行終了時に解放し、残存したロックを手動で解除する手段を提供しなければならない。
- ロックの解放(手動解除を含む)は、解放対象が自身の(または指定された)ロックであることを検証する条件付き操作で行わなければならない。
- ツールは各副作用(AWS への変更操作・ステート保存・ローカルファイルの書き込み)の直前にロックの所有権を検証し、WHEN 所有権を失っていた場合、当該副作用以降の処理を行わず中断しなければならない(fencing)。この検証は検証と副作用の間の競合窓を完全には排除できないベストエフォートであることを仕様上明記し、正本の一貫性はステート保存の compare-and-swap(競合した側の保存は必ず失敗する)およびスタック単位の進行中操作ガード(FR-2)によって保証しなければならない。
- ロックの手動解除は、保持していた実行が終了していることを利用者が確認した場合にのみ行う操作として位置づけ、ツールは実行時にロックの内容(実行 ID・開始時刻・実行者)と警告を表示しなければならない。手動解除後の再実行では、変更検知と変更セットの再作成によってステートと実環境の乖離が解消されること(冪等復旧)。
- WHEN AWS 操作は成功したがステート保存に失敗した場合(fencing 中断・CAS 競合・クラッシュ等)、次回実行は実スタックとの突合により自動で収束しなければならない: (a) IF `added` 分類のスタックキーに同名スタックが既に存在する場合、実スタックから検証可能な入力のすべて — 正規化したテンプレート(パース後の同値比較)、実効パラメータ、タグ、Capabilities — が希望する内容と一致する場合のみ、デプロイ成功として再同期しなければならない。希望側の実効パラメータは、希望テンプレートの scalar な `Parameters.<name>.Default` を文字列化した値を基底とし、設定の共通値とリージョン別上書きを解決した明示値で上書きしたものとする。Default がない未指定値は追加せず、NoEcho パラメータは Default／明示値のいずれも比較から除外する。object・array・intrinsic など非 scalar な Default は推測せず、実効値を比較不能として再同期を拒否しなければならない(fail-closed)。Default 補完はこの復旧比較だけに用い、設定オブジェクトまたは `inputsHash` のパラメータ部分を暗黙に変更してはならない。一致条件には、ツールが自動付与する管理タグ(FR-2)により当該スタックが自ステートの実行によって作成されたことの確認(由来確認)を含めなければならない。IF 管理タグによる由来確認ができない(欠如または不一致の)場合、他の入力がすべて一致しても再同期してはならない(fail-closed)。IF 実スタックから同値性を検証できない入力が 1 つでも存在する場合(対象テンプレートに `NoEcho` パラメータが宣言されている、または当該スタックに明示依存 `dependsOn` が 1 件以上ある場合)、ツールは再同期してはならず、当該対象を失敗として扱いインポート(FR-10)を案内しなければならない(fail-closed)。再同期してよいのは、検証可能な入力のすべてが一致し、**かつ検証不能な入力が存在しない**場合に限る。管理タグは「自ステートの実行が作成した」ことを示すだけで、**どの入力値で作成されたか**は証明しないためである。一つでも不一致がある場合は命名衝突または管理外スタックの可能性としてエラーとし、インポート(FR-10)を案内しなければならない。(b) IF `deleted` 分類のスタックが存在しない場合、削除成功としてステートから除去しなければならない。(c) 更新(UPDATE)は空変更セット(FR-2)により再同期されること。fail-closed 化の判断理由と以前の方式で生じる変更喪失経路は [ADR-0002](../decisions/0002-create-recovery-fail-closed.md) に記録する。
- ステートの保存は原子的に行わなければならない。IF ステートの破損(不完全な書き込み等)を検出した場合、ツールは変更系操作を拒否しなければならない(fail-closed)。
- ステートは単一の AWS アカウントに紐付けなければならない。WHEN 変更系操作を行う場合、ツールは接続先アカウント(FR-7)とステートに記録されたアカウント ID の一致を検証し、不一致の場合は実行を拒否しなければならない。複数アカウントを扱う場合は設定・ステートの組を分離する。
- WHEN スタック名の設定が変更された場合、ツールはこれを「旧スタック名のスタックの削除 + 新スタック名のスタックの新規作成」として扱わなければならない。削除は FR-6 の安全装置に従う。
- IF ステートが存在しない(初回実行)場合、ツールは全テンプレートを `added` として扱うか、既存スタックとの初期同期(FR-10)を促さなければならない。

### FR-2: 変更セットの作成

変更されたテンプレートに対して CloudFormation 変更セットを作成できること。

- WHEN `modified` のテンプレートに対して変更セット作成を実行した場合、ツールは対象スタックに `UPDATE` タイプの変更セットを作成しなければならない。
- WHEN `added` のテンプレートに対して変更セット作成を実行した場合、ツールは `CREATE` タイプの変更セットを作成しなければならない。
- IF 変更セットの Status が `FAILED` で、StatusReason を前後空白の除去により正規化した値が AWS の既知の「変更なし」定型文(`The submitted information didn't contain changes. Submit different information to create a change set.` / `No updates are to be performed.`)のいずれかに**完全一致**し、かつ `Changes` が空の場合に限り、ツールはこれをエラーではなく「変更なし」として扱い、後続処理をスキップしなければならない。既知文面に suffix が付く場合や、`Changes` が空でも別理由の場合を含む、それ以外の `FAILED` はエラーとして扱わなければならない。
- IF 対象スタックが `ROLLBACK_COMPLETE` 等のデプロイ不能ステータスの場合、ツールは明確なエラーメッセージと対処方法(スタック削除の必要性など)を提示しなければならない。
- テンプレートに IAM リソース等が含まれる場合に必要な Capability(`CAPABILITY_IAM` / `CAPABILITY_NAMED_IAM` / `CAPABILITY_AUTO_EXPAND`)を設定ファイルまたは CLI オプションで指定できなければならない。
- ツールが作成する変更セットは `cfnsync-<stateId:12hex>-<runId:16hex>-<UTC:YYYYMMDDTHHmmssSSS>` に完全一致しなければならない。残存変更セットはこの形式に完全一致する場合だけ所有権を判定し、形式不一致は判定不能として fail-closed に中断しなければならない。
- WHEN 対象スタックにツールが過去に作成した未実行の変更セットが残存する場合(dry-run の残骸や失敗した前回実行を含む)、ツールはそれを検出し、破棄した上で新たな変更セットを作成しなければならない。回収対象は、ツール自身が作成し、かつ自身と同一のステートに紐づくと検証できた変更セットに限り、他のツール・人手による変更セットに触れてはならない。IF 所有権を検証できない、または別のステート設定に紐づくツール由来の変更セットを検出した場合、ツールは変更セットを破棄せず中断しなければならない。この残存回収は**対象スタックが CloudFormation に既に存在する場合に限り**適用する。IF 対象スタックが CloudFormation に一切存在しない(真の新規 `CREATE`)場合、ツールは残存変更セットの列挙(`ListChangeSets`)を行わず、直接変更セットを作成しなければならない(存在しないスタックへの `ListChangeSets` は AWS 側のエラーとなるため)。
- IF 対象スタックが他の操作により `*_IN_PROGRESS` 状態にある場合、ツールは変更セットを作成せず、並行操作の存在をエラーとして報告しなければならない。
- ツールは、作成・更新するスタックに管理主体を識別するタグ(ステートの識別子を含む)を自動付与しなければならない。このタグは復旧時の同一性判定(FR-1)における由来(provenance)の確認に用いる。
- ツールは、変更セット未実行のまま残された空スタック(`REVIEW_IN_PROGRESS`)に対して、スタック自体の削除を行ってはならない。ツールは自身の所有と検証できた変更セットのみを個別に破棄し、新規作成型の変更セットを当該スタック上に再作成して続行しなければならない。IF 他主体の変更セットが存在する場合、変更セットを作成せずエラーとして停止しなければならない(fail-closed)。
- WHEN 変更セットを作成した場合、ツールは `CreateChangeSet` が返した変更セット ARN を保持し、待機・詳細取得・実行直前再検査・実行をその ARN で行わなければならない。WHEN 変更セットを実行する場合、ツールは実行の直前に対象スタックの未実行変更セットを再検査し、自身が作成した名前と ARN の双方が一致することを検証しなければならない。IF 自変更セットが欠落・差し替えされている、または他主体(ツール以外または別ステート)の変更セットが存在する場合、実行せずエラーとして停止しなければならない(CloudFormation の変更セット実行は同一スタックの他の変更セットを暗黙に削除するため)。再検査から実行までの競合窓は原理的に排除できないことを仕様に明記し、管理対象スタックに手動の変更セットを作成しない運用をドキュメントで求めなければならない。

### FR-3: 変更セットの差分表示

作成された変更セットの内容を人間が確認できる形式で出力できること。

- 変更セットに含まれるリソース単位の変更(Add / Modify / Remove)と、変更対象のプロパティを表示しなければならない。
- 変更セットの取得には `DescribeChangeSet` の `IncludePropertyValues=true` を指定し、CloudFormation が `ResourceChange.Details[].Target` に返したプロパティのパス、変更前後の値、変更種別、値の由来、評価方法、再作成要否をテキスト / JSON の両方へ出力しなければならない。CloudFormation が返さない値をテンプレートや実スタックから独自に補完・推測してはならない。
- CloudFormation が `ResourceChange` に返した `BeforeContext` / `AfterContext` は JSON 出力へ含めなければならない。
- IF リソースの置換(Replacement)が発生する変更が含まれる場合、ツールはそれを明確に警告として強調表示しなければならない。
- 出力形式として人間可読なテキストに加え、機械可読な JSON を選択できなければならない(GitHub Actions での PR コメント生成等に利用するため)。
- **FR-3-4:** WHEN `plan` または `deploy` が人間可読なテキスト差分を出力する場合、ツールは TTY / CI / パイプ・リダイレクトの別にかかわらず ANSI 色を既定で付与し、`Add` を緑、`Modify` を黄、`Remove` を赤、置換警告(`[REPLACEMENT]`)を太字の赤で表示しなければならない。
- **FR-3-5:** IF `plan` または `deploy` に `--no-color` を指定した場合、または値が空文字である場合を含め `NO_COLOR` 環境変数が存在する場合、ツールは人間可読なテキスト差分へ ANSI エスケープシーケンスを一切含めてはならない。これらの無色化指定は既定の色付きを常に上書きしなければならない。
- **FR-3-6:** WHEN `plan` または `deploy` に `--output json` を指定した場合、ツールは色設定にかかわらず ANSI エスケープシーケンスを一切含まない単一 JSON document を出力し、既存 JSON schema を維持しなければならない。
- **FR-3-7a:** WHEN `deploy` が承認要約(FR-5-6a〜g)を出力する場合、ツールは FR-3-4 / FR-3-5 と同じ色付け・無色化の規則を適用しなければならない。
- **FR-3-7b:** WHEN `--output json` を指定した `deploy` が承認要約を出力する場合、ツールは要約を標準エラー出力へ出力し、標準出力の単一 JSON document を変更してはならない。

### FR-4: 変更セットの実行(デプロイ)

作成済みの変更セットを実行し、デプロイを行えること。

- **FR-4-1:** WHEN 変更セットを実行した場合、ツールはスタック操作の完了(成功または失敗)まで待機し、スタックイベントを逐次出力しなければならない。
- **FR-4-2:** IF デプロイが失敗した場合、ツールは失敗の原因となったリソースとエラーメッセージを出力し、非ゼロの終了コードで終了しなければならない。デプロイ失敗 report の `errorMessage` は `CfnSyncError` の未装飾な公開本文だけから生成し、stackKey / region は各 stack entry の構造化フィールドへ分離しなければならない。内部 cause は report / progress / JSON に昇格させず、分類不能な例外は固定の安全な文言へ置換しなければならない。NoEcho redactor はこの公開本文へ適用する。
- **FR-4-3:** IF デプロイ失敗によりロールバックが発生した場合、ツールはロールバックの発生と結果を報告しなければならない。`rolledBack` は当該 `ExecuteChangeSet` より後に観測した構造化 StackEvent の resource status、または `waitForStack` が返す最終 StackStatus が、明示した rollback status (`ROLLBACK_COMPLETE` / `ROLLBACK_FAILED` / `UPDATE_ROLLBACK_COMPLETE` / `UPDATE_ROLLBACK_FAILED` / `IMPORT_ROLLBACK_COMPLETE` / `IMPORT_ROLLBACK_FAILED` と対応する実行中 status)の場合だけ `true` としなければならない。実行前の guard・復旧・設定・fencing 拒否、および rollback status を観測しない失敗は `false` とし、エラーメッセージ等の文字列や未知 status の部分一致を判定入力にしてはならない。

### FR-5: 変更セット作成とデプロイの一括実行

変更セットの作成から実行までを 1 コマンドで行えること。

- **FR-5-1:** WHEN 一括実行コマンドを実行した場合、ツールは変更検知 → 依存順序の解決 → 変更セット作成 → 差分表示 → 承認 → 実行を一連で行わなければならない。
- **FR-5-2a:** WHEN `deploy`(`--dry-run` を伴わない)を実行した場合、ツールは対象スタック全体の差分を先に確定させたうえで、**実行全体につき 1 回だけ**承認を求め、承認が得られた場合にのみ変更セットの実行およびスタック削除へ進まなければならない。対象スタックごとに個別の承認を求めてはならない(→ FR-12-3b)。判断理由と旧方式からの移行は [ADR-0001](../decisions/0001-deploy-approval-flow.md) および [CHANGELOG](../../CHANGELOG.md#unreleased) に記録する。
- **FR-5-2b:** IF `--auto-approve`(短縮形 `-y`)が指定された場合、ツールは承認を求めず実行しなければならない。
- **FR-5-3:** `--dry-run` オプションにより、変更セットの作成と差分表示までで停止(実行しない)できなければならない。
- **FR-5-4:** WHEN 一括実行(`--dry-run` による停止を含む)を行う場合、ツールは対象スタックごとに変更セット作成の開始・差分確定・実行開始・完了(成功/失敗/依存失敗等によるスキップ/変更なし)等の進捗を、対応するスタックキーを付して標準エラー出力へ逐次出力しなければならない。ただし、`plan` / `deploy --dry-run` が差分確定後に意図どおり停止すること自体はスキップ進捗として出力してはならない。この進捗出力は `--output json` 指定時の標準出力(差分・結果の JSON)に混入してはならない。承認を挟む場合でも、あるスタックについての段階の相対順序を変えてはならない。
- **FR-5-5a:** WHEN `deploy`(`--dry-run` を伴わない)を実行した場合、ツールは承認より前の段階(以下 Phase A)で `ExecuteChangeSet` および `DeleteStack` を行ってはならない。Phase A で許される AWS への副作用は、自ステートに紐づく残存変更セットの回収(FR-2)と変更セットの作成・削除だけである。承認後の段階(以下 Phase B)は依存順(FR-9)で実行しなければならない。
- **FR-5-5b:** ツールは Phase A において、**すでに事実確認が完了した内容**の再同期(reconciliation)に限りステートへ保存してよい。ここで「事実確認が完了した」とは、**AWS が返した応答そのもの**、または **cfnsync が全入力について完全に比較できた結果**に基づく記録に限る。該当するのは FR-5-5b1 / FR-5-5b2 / FR-5-5b3 の 3 つだけであり、これらは変更の意図の記録ではなく既成事実の記録であるため承認の対象ではない。承認拒否によってこの再同期が失われると FR-1 / NFR-3 の自動収束が働かなくなるため、拒否時もこの保存を取り消してはならない。
- **FR-5-5b1:** WHEN Phase A が空変更セット(FR-2 の既知の「変更なし」定型文)を検出した場合、ツールは変更なし確認をステートへ再同期してよい。これは CloudFormation 自身が NoEcho を含む実パラメータで比較した結果だからである。
- **FR-5-5b2:** WHEN Phase A が削除対象スタックの不在を検出した場合、ツールはステートからの当該エントリ除去を再同期してよい。これは `DescribeStacks` が当該スタックを返さないという事実だからである。
- **FR-5-5b3:** WHEN Phase A の CREATE 復旧(FR-1)で、対象テンプレートに `NoEcho` パラメータが宣言されておらず、かつ当該スタックの `dependsOn` が空である場合、ツールは再同期をステートへ保存してよい。この条件下では全入力を実スタックと完全に比較できる。
- **FR-5-5b4:** IF Phase A の CREATE 復旧で検証不能な入力が 1 つでも残る場合(`NoEcho` パラメータが宣言されている、または `dependsOn` が空でない)、ツールはこれを事実確認済みとして扱ってはならず、ステートを保存せず FR-1 に従って fail-closed に失敗させなければならない。
- **FR-5-5b5:** WHEN FR-5-5b1〜b3 の再同期を保存する場合、ツールは保存の直前に fencing 検証(FR-1)を行わなければならない。IF ロックの所有権を失っていた場合、保存してはならない。
- **FR-5-5b6:** WHEN FR-5-5b1〜b3 の再同期を保存する場合、ツールは compare-and-swap(FR-1)で保存しなければならない。IF 読込時点からの世代競合を検出した場合、上書きせずエラーとしなければならない。
- **FR-5-5c:** ツールは、実行の成功記録(`ExecuteChangeSet` または `DeleteStack` の結果としてのステート更新)を Phase B でのみ保存しなければならない。承認前にこれを保存してはならない。
- **FR-5-6a:** WHEN 承認を求める場合、ツールは解決済みの接続先(アカウント ID・許可済みリージョン)を要約に含めなければならない。
- **FR-5-6b:** WHEN 承認を求める場合、ツールは対象スタックごとの操作種別(create / update / delete)を要約に含めなければならない。
- **FR-5-6c:** WHEN 承認を求める場合、ツールは対象スタックごとのリソース単位の差分を要約に含めなければならない。
- **FR-5-6d:** WHEN 承認を求める場合、ツールはリソース置換(Replacement)が発生する変更を警告として要約に含めなければならない。
- **FR-5-6e:** WHEN 承認を求める場合、ツールは削除対象を、`--allow-delete` の有無(実際に削除するのか警告に留まるのか)を明示したうえで要約に含めなければならない。
- **FR-5-6f:** WHEN 承認を求める場合、ツールは要約および承認プロンプト(入力エコーを含む)を標準エラー出力へ出力し、`--output json` 指定時の標準出力(単一 JSON document)へ混入させてはならない。
- **FR-5-6g:** WHEN 承認を求める場合、ツールは要約に含める AWS 由来の文字列へ、report へ格納する場合と同じ NoEcho マスク(NFR-4)を適用した後に提示しなければならない。
- **FR-5-7a:** IF 変更セットの作成に成功したがリソース単位の差分が 0 件である場合(Outputs / Export のみの変更等)、ツールはこれを「変更なし」として扱ってはならず、実行対象に含めなければならない。当該変更セットをスキップすると Export が作成されず後続スタックの実行が失敗するためである。空変更セット(FR-2 の既知の「変更なし」定型文で `FAILED` となったもの)だけが「変更なし」である。
- **FR-5-7b:** WHEN FR-5-7a の対象を承認要約または人間可読なテキスト差分に提示する場合、ツールは「変更あり」として扱ったうえで、CloudFormation リソース差分が 0 件であること(Outputs 等の非リソース変更を含みうること)を利用者が判別できる表示にしなければならない。`no-change` の表示と同一または紛らわしい文言にしてはならない。
- **FR-5-7c:** FR-5-7b の判別表示は、操作種別が `create` または `update` の対象に限って適用しなければならない。削除プレビュー(`delete`)はリソース差分を持たないことが正常であり、この表示の対象としてはならない。
- **FR-5-7d:** FR-5-7b の判別は、出力の整形(レンダラ)においてのみ行わなければならない。ツールは `DeployReport` のデータ(`StackDiff.warnings` への警告追加、`operation` への新しい値の追加等)を変更してはならない。これらは JSON 出力の対象であり、データ側で区別すると FR-5-16 に違反するためである。
- **FR-5-7e:** WHEN 人間可読なテキスト差分または承認要約に操作種別が `delete` の対象を提示する場合、ツールはリソース単位の差分行が 0 件であることを理由に「変更なし」と表示してはならず、スタック全体が削除対象であることを利用者が判別できる表示にしなければならない。この文言は FR-5-7b の 0 件注記とも `no-change` の表示とも区別できなければならない(3 者は同一の出力に混在しうる)。承認は削除の可否を人間に問う場面であり、削除は最も不可逆な操作であるため、`(変更なし)` は承認判断を誤らせる。FR-5-7c は FR-5-7b の 0 件注記の適用対象を `create` / `update` に限る規定であり、本項が求める削除専用の表示を妨げるものではない。本項の表示は実行の可否を断定してはならない — 実際に削除するのか警告に留まるのか(`--allow-delete` の有無・`--dry-run`)は FR-5-6e の削除注記と `StackDiff.warnings` が担う。本項の判別は FR-5-7d と同一の制約に従い、出力の整形(レンダラ)においてのみ行わなければならず、`DeployReport` のデータ(`StackDiff.warnings` / `operation` 等)を変更してはならない(FR-5-16)。
- **FR-5-8a:** IF Phase B で実行予定の変更セット実行およびスタック削除が 1 件も存在しない場合(全対象が変更なしの場合、および再同期のみが必要な場合を含む)、ツールは承認を求めてはならない。
- **FR-5-8b:** WHEN FR-5-8a に該当する場合、ツールは FR-5-5b の再同期を行ったうえで終了コード 0 で終了しなければならない。
- **FR-5-9a:** IF `--dry-run` が指定された場合、または `plan` を実行した場合、ツールは何も実行しないため承認を求めてはならない。
- **FR-5-9b:** `--dry-run` は `plan` と同一の変更セットライフサイクルに従わなければならない。すなわち、対象ごとに差分を取得した直後に自身の変更セットを削除しなければならず、承認を行わない以上、Phase A の保持経路(FR-5-5a)を用いてはならない。
- **FR-5-10a:** WHEN 承認が拒否された場合、ツールは Phase A で作成した自身の変更セットをすべて削除しなければならない。
- **FR-5-10b:** WHEN 承認が拒否された場合、ツールは承認の対象であった AWS の変更操作(`ExecuteChangeSet` および `DeleteStack`)を 1 件も行ってはならない。ただし Phase A は変更セットの作成・削除を行っており、`CREATE` 型変更セットの作成により `REVIEW_IN_PROGRESS` のスタックの殻が残る場合があるため、「AWS への副作用が皆無である」と主張してはならない。
- **FR-5-10c:** WHEN 承認が拒否された場合、ツールは未実行スタックの結果を `skipped` として報告し、終了コード 0 で終了しなければならない。承認拒否は利用者の明示的な意思による正常終了であり、失敗として扱ってはならない(CI では FR-12-3b により `--auto-approve` が必須のため、非対話実行で拒否は発生しない)。
- **FR-5-11:** IF 承認拒否後のクリーンアップ(変更セットの削除)に失敗した場合、ツールはその事実を報告し、終了コード 1 で終了しなければならない。残存した変更セットは次回実行の残存回収(FR-2)で回収されなければならない。
- **FR-5-12a:** IF Phase A のいずれかの対象で失敗が発生した場合、ツールは承認を求めず、Phase B へ進まず、終了コード 1 で終了しなければならない(fail-closed)。差分が不完全な計画に対して不可逆な操作の承認を求めてはならないためである。
- **FR-5-12b:** ツールは Phase A の失敗に対し、`--on-failure` の値にかかわらず FR-5-12a に従って実行全体を中断しなければならない。`--on-failure` の適用範囲は Phase B(実行)に限られる。計画失敗を縮退実行しない理由は [ADR-0001](../decisions/0001-deploy-approval-flow.md)、互換性への影響は [CHANGELOG](../../CHANGELOG.md#4---on-failure-の適用範囲を実行段階へ限定) に記録する。
- **FR-5-12c:** WHEN FR-5-12a により中断する場合、ツールは Phase A で作成済みの自身の変更セットをすべて削除しなければならない。
- **FR-5-13:** IF 承認が必要(`--dry-run` でも `--auto-approve` でもない)であるにもかかわらず、実行環境から承認手段が与えられていない場合、ツールは AWS・ステートバックエンドへの一切のアクセスの前にエラーで終了しなければならない(fail-closed)。
- **FR-5-14a:** WHEN 承認を待つ場合、ツールはステートロック(FR-1)を保持し続けなければならない。
- **FR-5-14b:** 承認待ちの間に他の主体が実スタックを変更しうるため、ツールは承認時点の差分と実行時点の実状態の一致を保証してはならない。防御は FR-5-17 の実行直前再検査に限られ、それ以上の保証を主張してはならない。
- **FR-5-15a:** `Fn::ImportValue` は変更セットの作成時には解決されず `{{changeSet:KNOWN_AFTER_APPLY}}` として保留され、CloudFormation は参照先 Export の実在を検証しない。したがって依存先スタックがこの実行で新規作成される場合であっても、ツールは Phase A で当該対象の変更セットを作成できなければならず、これを回避するための事前判定・遅延実行の機構を持ってはならない。
- **FR-5-15b:** WHEN 承認要約または差分出力に FR-5-15a の保留値を提示する場合、ツールは CloudFormation が返した値をそのまま提示し、独自に解決・補完してはならない(FR-3)。承認時点でこれらのプロパティの最終値が確定していないこと(terraform の "known after apply" と同じ性質)は、利用者向けの既知の性質として文書化しなければならない。
- **FR-5-16:** ツールは `--output json` が出力する deploy report のフィールド(`connection` / `diffs` / `events` / `result`)の構造および要素の順序を変更してはならない。追加してよいのは、承認拒否時の `cancelled`(FR-12-6c1)と再同期発生時の開示(FR-5-18)の 2 つだけであり、いずれも**該当する事象が発生した実行にのみ**出力しなければならない。したがって拒否も再同期も起きなかった実行の JSON はこれらの追加フィールドを含まない基準 schema と一致しなければならない。
- **FR-5-17a1:** WHEN Phase B で各対象の変更セットを実行する場合、ツールは実行の直前に、自身の変更セットの**名前**が Phase A の作成時の値と完全一致することを再検査しなければならない(FR-2)。Phase A の検査結果を再利用してはならない。
- **FR-5-17a2:** WHEN Phase B で各対象の変更セットを実行する場合、ツールは実行の直前に、自身の変更セットの **ARN** が Phase A の作成時の値と完全一致することを再検査しなければならない(FR-2)。名前が一致していても ARN が異なる場合は実行してはならない。
- **FR-5-17a3:** WHEN Phase B で各対象の変更セットを実行する場合、ツールは実行の直前に、自身の変更セットが対象スタックの**唯一の未実行変更セット**であることを再検査しなければならない。他主体(ツール以外または別ステート)の変更セットが存在する場合は実行してはならない(FR-2: `ExecuteChangeSet` は同一スタックの他の変更セットを暗黙に削除するため)。
- **FR-5-17b:** WHEN Phase B で `UPDATE` を実行する場合、ツールは実行の直前に対象スタックの `stackId`(ARN)がステートの記録と一致することを再照合しなければならない。
- **FR-5-17c1:** WHEN Phase B で `UPDATE` を実行する場合、ツールは実行の直前に、対象スタックの状態が明示的な allowlist(`CREATE_COMPLETE` / `UPDATE_COMPLETE` / `UPDATE_ROLLBACK_COMPLETE` / `IMPORT_COMPLETE` / `IMPORT_ROLLBACK_COMPLETE`)のいずれかであることを再確認しなければならない。allowlist 外の状態はすべて実行せず fail-closed に停止しなければならない。`*_IN_PROGRESS` の否定だけでは不十分である — 承認待ちの間に対象が `ROLLBACK_COMPLETE` 等の実行不能な終端状態へ遷移しうるためである。
- **FR-5-17c2:** WHEN Phase B で `CREATE` を実行する場合、ツールは実行の直前に、対象が**自身の変更セットに対応する `REVIEW_IN_PROGRESS` の殻**、またはスタック未作成であることを再確認しなければならない。別のスタックへ差し替えられていた場合は実行せず fail-closed に停止しなければならない。
- **FR-5-17d:** WHEN Phase B で各副作用を行う場合、ツールはその直前にロックの所有権を再検証しなければならない(FR-1 の fencing)。承認待ちの間に force-unlock が行われた場合、以降の副作用を行わず中断しなければならない。
- **FR-5-17e:** WHEN Phase B で各対象を実行する場合、ツールは再検査を次の順序で行わなければならない: (1) `DescribeStacks` によるスタックの存在・`stackId`・状態の確認(FR-5-17b / FR-5-17c)、(2) `ListChangeSets` の全ページ走査による自変更セットの name / ARN の完全一致と、それが唯一の未実行変更セットであることの確認(FR-5-17a)、(3) ロック所有権の検証(FR-5-17d)、(4) `ExecuteChangeSet`。この順序は、状態の確認を変更セットの確認より先に行うことで実行不能な状態を早期に排除し、fencing を副作用の直前に置くために規範として固定する。
- **FR-5-18a:** WHEN FR-5-5b の再同期がステートへ保存された場合、ツールはその事実を deploy report の**機械可読な出力(JSON)**へ開示しなければならない。開示には対象のスタックキー、再同期の種別(空変更セット / 削除済み同期 / CREATE 復旧)、およびステートを更新したか否かを含める。承認拒否時(FR-5-10)にも永続ステートは変わりうるため、利用者が標準出力から「何が変わったか」を復元できなければならない。
- **FR-5-18b:** WHEN FR-5-5b の再同期がステートへ保存された場合、ツールはその事実を**人間可読なテキスト出力**にも、対象のスタックキー・種別・ステート更新の有無を列挙する形で開示しなければならない。既定の出力形式は text であり、JSON だけに開示すると既定の利用者が state の変化を観測できないためである。
- **FR-5-18c:** IF 再同期が 1 件も発生しなかった場合、ツールは FR-5-18a の開示フィールドを出力に含めてはならず、FR-5-18b の開示をテキスト出力へ追加してはならない(FR-5-16 の例外として、再同期が発生した実行だけが基準となる出力と差分を持つ)。
- **FR-5-18d:** ステートへの初回 `accountId` 記録(FR-1 / FR-7)は FR-5-5b の再同期とは別種の既存の安全保存であり、FR-5-18a / FR-5-18b の開示の対象に含めてはならない。
- **FR-5-19a:** IF `DeployDeps.approve` が reject または throw した場合、ツールは Phase A で作成した自身の変更セットを、作成時に保持した ARN を指定してすべて削除しなければならない。
- **FR-5-19b:** IF `DeployDeps.approve` が reject または throw した場合、ツールは `ExecuteChangeSet` を 1 件も行ってはならない。
- **FR-5-19c:** IF `DeployDeps.approve` が reject または throw した場合、ツールは `DeleteStack` を 1 件も行ってはならない。
- **FR-5-19d:** IF `DeployDeps.approve` が reject または throw した場合、ツールは Phase B で実行予定だったすべての対象を `skipped` として報告しなければならない。
- **FR-5-19e:** IF `DeployDeps.approve` が reject または throw した場合、ツールは承認処理の失敗を `failed` として report に含めなければならない。
- **FR-5-19f:** IF `DeployDeps.approve` が reject または throw した場合、ツールは終了コード 1 で終了しなければならない。
- **FR-5-19g:** IF `DeployDeps.approve` の失敗後に自身の変更セットを削除できない対象がある場合、ツールはクリーンアップ失敗と次回実行の残存回収に委ねることを report に含めなければならない。
- **FR-5-19h:** WHEN `DeployDeps.approve` が `CfnSyncError` により失敗した場合、ツールは `CfnSyncError.publicMessage` に既知のすべての NoEcho 実効値の redactor を適用し、内部 cause および未マスクの値を report / progress / JSON に含めてはならない。
- **FR-5-19i:** WHEN `DeployDeps.approve` が分類不能な例外により失敗した場合、ツールはその生メッセージを report / progress / JSON に含めず、固定の安全な文言へ置換しなければならない。

### FR-6: スタックの削除

テンプレートファイルの削除をトリガーに、対応するスタックを削除できること。

- WHEN `deleted` と判定されたテンプレートが存在する場合、ツールは対応するスタックを削除対象として差分表示に含めなければならない。
- スタックの削除は、明示的なオプション(例: `--allow-delete`)が指定された場合にのみ実行しなければならない。デフォルトでは削除対象の存在を警告として報告し、削除は行わない(安全側に倒す)。
- IF スタックに削除保護(Termination Protection)が有効な場合、ツールは保護を自動解除せず、エラーとして報告しなければならない。
- 削除順序は、現在のテンプレート群から構築した依存関係グラフに加え、ステートに保存された前回成功時点のグラフ(FR-8。削除対象スタックが保持していた依存辺を含む)を統合して決定し、依存の逆順で実行しなければならない。
- IF 削除対象スタックの依存情報がステートから復元できない、または曖昧な場合、ツールは当該スタックの削除を拒否し、手動対応が必要であることを報告しなければならない。
- スタック削除は FR-7 の接続先検証(fail-closed)の対象であり、`--allow-delete` は接続先検証を通過した場合にのみ有効である。

### FR-7: 認証・接続設定

AWS への認証は標準的な方法で行えること。

- **FR-7-1:** `~/.aws/config` のプロファイルを CLI オプション(例: `--profile`)または環境変数 `AWS_PROFILE` で指定して認証できなければならない。
- **FR-7-2:** プロファイル未指定の場合は AWS SDK の標準クレデンシャルチェーン(環境変数 → プロファイル → IAM ロール等)に従わなければならない。これにより GitHub Actions の OIDC(`aws-actions/configure-aws-credentials`)で払い出された一時クレデンシャルがそのまま利用できること。
- **FR-7-4:** ツール自身がクレデンシャルを独自に保存してはならない。

誤接続防止(接続先検証):

- **FR-7-5:** 設定ファイルで、操作を許可する AWS アカウント ID および許可するリージョン(複数指定可)を指定しなければならない。この設定はすべての変更系操作の前提条件である。
- **FR-7-6:** WHEN 変更系操作(変更セットの作成・実行・スタック削除)を行う場合、ツールは STS `GetCallerIdentity` により接続先アカウントを解決し、許可設定と照合しなければならない。IF 許可設定が未設定・不一致・解決不能のいずれかの場合、ツールは変更セットの作成を含む一切の変更系操作を行わず、エラーで終了しなければならない(fail-closed)。
- **FR-7-7:** 読み取り専用操作(status / graph / import 等)は許可設定なしでも実行してよい。ただし解決した接続先を出力に含めなければならない。IF 操作がステートへの書き込みを伴う場合(import)、FR-1 のアカウント照合とロック取得を行わなければならない。
- **FR-7-8:** 解決した接続先(アカウント ID・リージョン)を実行ログおよび JSON 出力に含めなければならない(クレデンシャル等の秘匿情報は含めない)。STS がアカウント ID を返した時点で接続先は解決済みとし、その後に `allowedAccounts` / `allowedRegions` / state account の照合で拒否された場合も report / JSON には解決済み ID を保持しなければならない。`(unresolved)` は STS が ID を返せない場合、または許可設定未設定等により STS 呼び出し前に停止した場合だけとする。接続先の表示は guard の成否を変えず、拒否後の lock・state・CloudFormation 副作用はゼロでなければならない。

対象リージョンの決定(スタックキーの安定性):

- **FR-7-9a:** WHEN CLI オプション `--region` を指定した場合、ツールは対象リージョンとしてその値を採用し、設定ファイルの `defaultRegion` を上書きしなければならない。
- **FR-7-9b:** IF `--region` を指定しない場合、ツールは対象リージョンとして設定ファイルの `defaultRegion` を採用しなければならない。
- **FR-7-9c:** IF 環境変数 `AWS_REGION` または `AWS_DEFAULT_REGION` が設定されている場合であっても、ツールはこれらを対象リージョンの決定に使用してはならない。同一の設定ファイルと同一の CLI 引数に対して、ツールが解決する対象リージョンおよびスタックキー(`<テンプレート相対パス>@<リージョン>`)は、これらの環境変数の有無・値によって変化してはならない。管理単位であるスタックキーは設定ファイルを正本とし、その上書きは CLI で明示した場合(FR-7-9a)に限る。
- **FR-7-9d:** WHEN AWS クライアント(CloudFormation / STS)を生成する場合、ツールは FR-7-9a / FR-7-9b で解決した対象リージョンを明示的に渡さなければならず、AWS SDK 側の既定リージョン解決に委ねてはならない。

### FR-8: 依存関係マッピングの出力

テンプレート間の依存関係を解析し、マッピングとして出力できること。

- ツールはテンプレートの `Export`(Outputs)と `Fn::ImportValue` を解析し、スタック間の依存関係グラフを構築しなければならない。
- 自動解析で表現できない依存関係(パラメータ経由の参照等)のために、設定ファイルで明示的に依存関係を宣言できなければならない。
- 依存関係マッピングを人間可読な形式(テキストツリー等)および機械可読な形式(JSON)で出力できなければならない。
- IF 依存関係に循環が存在する場合、ツールは循環に含まれるスタックを明示してエラーとしなければならない。
- WHEN デプロイまたは削除が成功した場合、ツールはその時点の依存関係グラフ(または再構築に必要な Export / Import 情報)をステートに保存しなければならない。テンプレートファイルが削除された後でも、そのスタックが保持していた依存辺を参照できるようにするためである(→ FR-6)。
- WHEN 依存関係マッピングを人間可読なテキスト形式で出力する場合、ツールはスタックをトポロジカル順序に基づく階層(レベル)へグループ化し、同一レベル内のスタックが並列デプロイ可能であることが分かる形式(`Lv0`, `Lv1`, ... の見出し)で出力しなければならない。複数のスタックが同一の依存元を共有する場合(diamond 依存)でも、依存関係の記述を重複させてはならない。機械可読な JSON 出力(ノード・辺の構造)はこの表示形式の変更による影響を受けない。
- **FR-8-7**: WHEN `Outputs.*.Export.Name` または `Fn::ImportValue` が、テンプレートの `Parameters` に宣言された `Type: String` / `Type: Number` パラメータへの `Ref`、または当該パラメータを含む文字列形式の `Fn::Sub` で表現されている場合、ツールはテンプレートの scalar な `Default` に対象リージョンの実効 `parameters`(`parameters` に `regionOverrides.<region>.parameters` を後勝ちで反映したもの)を上書きした値を使って名前を解決し、依存関係グラフへ反映しなければならない。明示された実効値は空文字を含めて `Default` より優先し、明示値が `__REQUIRED__` の場合は `Default` へフォールバックしてはならない。IF 値が確定できない、パラメータが `NoEcho`、型が `String` / `Number` 以外、または式が対応範囲外の場合、ツールは警告を出し、その Export / Import だけを依存計算から除外しなければならない。他の解決可能な自動依存および明示 `dependsOn` の計算は継続しなければならない。WHEN 解析警告が残るスタックに明示 `dependsOn` が1件以上ある場合、ツールは利用者が依存関係を補完済みとみなし、当該スタックを解析不完全として保存してはならない。

### FR-9: 依存順序に従ったデプロイ

デプロイは依存関係マッピングのトポロジカル順序に従って実行されること。

- WHEN 複数のスタックがデプロイ対象の場合、ツールは依存されるスタックを先に、依存するスタックを後にデプロイしなければならない。
- IF あるスタックのデプロイが失敗した場合、そのスタックに依存する後続スタックのデプロイは中止し、依存関係のない他のスタックの扱い(継続 or 全体中止)はオプションで選択できなければならない。
- 相互に依存のないスタックの並列デプロイは将来拡張とし、初期リリースでは直列実行でよい(設計上は並列化を妨げない構造とする)。

### FR-10: 既存スタックのインポート(初期同期)

既存運用中のプロダクトを対象とするため、すでにデプロイ済みのスタックを再作成せずに管理下に置けること。インポートは実環境を正として行い、実環境とローカルの差異を隠蔽してはならない。

- WHEN インポートを実行した場合、ツールは既存スタックから以下を取得し、ローカルの設定ファイル(FR-11)に反映しなければならない: スタック名、現在のパラメータ値、タグ、必要な Capabilities。
- IF パラメータが `NoEcho` の場合、実値は取得できないため、設定ファイルには要入力を示すプレースホルダを記録しなければならない。マスク値(`****`)をそのまま実値として書き込んではならない。
- WHEN インポートを実行した場合、ツールはデプロイ済みテンプレート(`GetTemplate`)とローカルのテンプレートファイルを比較しなければならない。
- IF デプロイ済みテンプレートとローカルテンプレートに差分がある場合、デフォルトではエラーとし、明示的なオプションにより以下のいずれかを選択できなければならない: (a) デプロイ済みテンプレートでローカルファイルを上書きする、(b) 差分を承知の上でローカルファイルを維持し、その差分が次回の plan で変更として顕在化するようにステートを記録する。
- IF ローカルにテンプレートファイルが存在しないスタックを取り込む場合、ツールはデプロイ済みテンプレートをローカルファイルとして書き出せなければならない。
- ステートには検証済みの対応関係と、デプロイ済みテンプレートの内容に基づくハッシュを記録しなければならない。未デプロイのローカル内容を「デプロイ済み」としてステートに記録してはならない。
- インポートは AWS に対して読み取り専用でなければならない。書き込み対象はローカルの設定ファイル・ステート・テンプレートファイルのみとする。
- WHEN インポートを実行した場合、ツールは STS により接続先アカウントを解決し、ステートに記録されたアカウント ID と照合しなければならない(FR-1)。照合はロック取得後に再読込したステートに対して行い、ロック取得前に読んだステートを判断に使用してはならない。IF 不一致の場合、設定ファイル・ステート・テンプレートファイルへの一切の書き込みを行わずエラーで終了しなければならない。IF ステートが未作成(初回)の場合、解決したアカウント ID をステートの作成と同一ロック区間内の保存操作(compare-and-swap)で記録しなければならない。
- インポートはステートを書き込むため、ロックの取得(FR-1)を変更系操作と同様に行わなければならない。
- IF テンプレートに対応するスタックが存在しない場合、そのテンプレートは `added`(新規作成対象)として扱わなければならない。

### FR-11: 設定ファイル

テンプレートとスタックの対応やデプロイパラメータを設定ファイルで管理できること。

- テンプレートファイルごとに以下を設定できなければならない: スタック名、デプロイ先リージョン(複数可、FR-13)、パラメータ(またはパラメータファイルへの参照)、タグ、Capabilities、明示的な依存関係、リージョンごとのパラメータ・タグの上書き。
- 全体設定として、ステートバックエンド(`local` / `s3` とその接続情報)を設定できなければならない(FR-1)。
- スタック名が未設定の場合の規約(例: ファイル名からの導出)を持ち、設定を最小限で運用できなければならない。
- 設定ファイルはリポジトリにコミット可能なテキスト形式(YAML 等)でなければならない。
- 設定ファイルに不備がある場合(存在しないテンプレートへの参照、必須項目欠落等)、ツールは実行前の検証で検出し、対象キーを含む単一の人間可読な `ConfigError` として具体的なエラーを報告しなければならない。同じ本文・スタックキー・原因を重複表示してはならず、zod issue 配列を出力してはならない。
- `stacks` のキーであるテンプレートパスは設定ファイルのディレクトリを基準とする相対パスに限り、絶対パス・NUL を含むパス・正規化後に `..` から始まるパスを設定検証時に対象キーを示す `ConfigError` で拒否しなければならない。サブディレクトリを含む正当な相対パスは許可する。
- WHEN テンプレートを読み取りまたは import で書き込む場合、解決先の実パス(未作成なら既存の最長親ディレクトリの realpath から解決したパス)が設定ファイルのディレクトリ配下であることを検証しなければならない。IF シンボリックリンク等を経由して範囲外へ到達する場合、一切のローカル書き込みを行わずエラーで終了しなければならない。
- 全体設定として、すべての管理対象スタックへ既定で付与するタグ(デフォルトタグ)を設定できなければならない。デフォルトタグは各スタックの実効タグへマージされた上でデプロイされなければならない。IF デフォルトタグとスタックごとのタグでキーが重複する場合、スタックごとの値を優先しなければならない(エラーとはしない)。
- デフォルトタグの変更は、それを付与される各スタックのデプロイ入力の変更として変更検知(FR-1)に反映されなければならない。
- **FR-11-10a:** IF 解決済みのデプロイ対象のうち 2 つ以上が同一の (リージョン, スタック名) を指す場合、ツールは設定検証の段階で、AWS およびステートバックエンドへの一切のアクセスの前に、対象キーを含む `ConfigError` として拒否しなければならない。同一リージョン内でスタック名は物理スタックの一意識別子であり、複数のスタックキーが同一の物理スタックを指すことを許すと、変更セットを事前作成する実行(FR-5-5a)において、後続の対象による残存変更セット回収(FR-2)が先行対象の未実行変更セットを自ステート由来の残骸として削除してしまうためである。
- **FR-11-10b:** IF 設定検証を通過した後、実行計画中の create / update / delete の**任意の 2 操作**が同一の (リージョン, スタック名) を指し、かつ**少なくとも一方が create または update** である場合、ツールは AWS への副作用の前に fail-closed に拒否し、リネーム移行の手順を案内しなければならない。テンプレートパスの変更は通常「旧ステート由来の delete 1 件 + 新しい設定由来の create 1 件」として計画されるため、create / update 同士の重複だけを見る条件では捕捉できない。削除対象が現に管理下にある物理スタックを指す場合の拒否(FR-6)と整合させる。
- **FR-11-10c:** ツールは FR-11-10b の条件に該当しない構成を拒否してはならない。すなわち、2 操作がいずれも delete である場合、および対象が異なる (リージョン, スタック名) を指す場合は正常な構成として扱わなければならない。異なるスタック名へのリネーム(FR-1)、同一スタック名を複数リージョンへ配置する構成(FR-13)、`--region` による既定リージョン上書き後の解決結果、`stackNamePrefix` からの導出は、いずれも拒否の対象ではない。

### FR-12: CLI インターフェース

- **FR-12-1:** ツールは少なくとも以下に相当するサブコマンドを提供しなければならない:
  - 変更検知結果の表示(status 相当)
  - 変更セット作成+差分表示(plan / diff 相当)
  - デプロイ実行(deploy / apply 相当)。既定は「差分表示 → 承認 → 実行」の対話フローとする(FR-5-2a)
  - 依存関係マッピング表示(graph 相当)
  - 既存スタックのインポート(import 相当)
- **FR-12-2:** 終了コードは CI で判定可能なように定義しなければならない(例: 0 = 成功/変更なし、1 = 実行エラー、2 = 差分あり(dry-run 時)等)。
- **FR-12-3a:** すべてのコマンドは TTY なしの環境(CI)で動作しなければならない(`deploy` は FR-12-3b の条件下でのみ制限される)。
- **FR-12-3b:** IF TTY のない環境で `deploy`(`--dry-run` を伴わない)が `--auto-approve` を指定せずに実行された場合、ツールは AWS・ステートバックエンドへ一切アクセスせず、CLI 境界で `CliUsageError` として終了コード 1 で終了しなければならない(fail-closed)。CI では `--auto-approve` の指定を必須とする。
- **FR-12-3c:** FR-12-3b の判定は変更の有無より前に行わなければならない。結果として、変更が 1 件もない非 TTY 実行も `--auto-approve` なしではエラーとなる。旧方式からの移行は [CHANGELOG](../../CHANGELOG.md#2-非-tty-の-deploy-は---auto-approve-が必須) に記録する。
- **FR-12-4:** ツールは自身のバージョン(`package.json` の version)を `--version`(短縮形 `-v`)で表示し、終了コード 0 で終了しなければならない。
- **FR-12-5:** WHEN いずれかのサブコマンド(`status` / `plan` / `deploy` / `graph` / `import` / `force-unlock`)の
  `--help` を表示した場合、ツールは当該サブコマンド固有のオプションに加え、共通オプション(`--config` /
  `--profile` / `--region` / `--output`)を一覧として表示しなければならない。
- **FR-12-6a:** WHEN 有効な `--output json` を指定した実行が、コマンド固有 result を生成する前に失敗した場合、ツールは設定読込・設定検証、Commander 引数検証、未知 subcommand、依存循環等の例外を、設計書 §9 の共通エラー schema により標準出力へちょうど 1 個の JSON document として出力しなければならない。
- **FR-12-6b:** WHEN 有効な `--output json` を指定した実行がコマンド固有 result を生成できた場合、ツールは終了コードにかかわらず既存 JSON schema を維持した単一 document を標準出力へ出力し、JSON 本体を標準エラーへ移してはならない。進捗・警告・人間向け診断は標準エラーへ分離する。import のロック取得・解放 warning は、JSON 選択時には内部 cause を含まない安全な本文を使い、text 選択時には `CfnSyncError.message` の装飾済み診断を使う。`--help` / `--version` は text・終了コード 0 とし、有効な JSON 選択が成立しない `--output` 自体の不正値は本契約の対象外とする。
- **FR-12-6c1:** WHEN `deploy` の承認(FR-5-2a)を利用者が拒否し、かつ有効な JSON 選択がある場合、ツールは標準出力へ deploy report の既存 JSON schema に `cancelled: true` を追加した単一 document をちょうど 1 個出力し、終了コード 0 としなければならない。拒否時も Phase A で確定した差分と `skipped` 結果を JSON から失わせてはならない。
- **FR-12-6c2:** WHEN `deploy` の承認を利用者が拒否し、かつ text 選択の場合、ツールは標準エラーへ `Deployment cancelled.` を出力したうえで、標準出力へ deploy report を出力し、終了コード 0 としなければならない。
- **FR-12-6c3:** 承認拒否時の JSON に `exitCode` および `message` フィールドが存在してはならない。出力契約の移行例は [CHANGELOG](../../CHANGELOG.md#3-承認拒否時の出力契約の置換) に記録する。
- **FR-12-6d:** 有効な JSON 選択は `--output json` と `--output=json` の両記法を認識しなければならない。
- **FR-12-6e:** 有効な `--output` はサブコマンドの前後どちらに指定しても同じ選択として扱わなければならない。
- **FR-12-6f:** IF `--output` が複数指定された場合、ツールは最後の指定を採用しなければならない。
- **FR-12-6g:** ツールは `--config` 等の値付きオプションの値として消費された文字列 `--output=json` を JSON 選択として扱ってはならない。
- **FR-12-6h:** WHEN `--help` または `--version` を指定した場合、`--output json` が同時に現れても JSON 契約の対象外とし、text を出力して終了コード 0 としなければならない。
- **FR-12-7:** WHEN `plan --help` または `deploy --help` を表示する場合、ツールは ANSI 色を無効化する `--no-color` オプションを一覧に含めなければならない。このオプションを他のサブコマンドへ提供してはならない。
- **FR-12-8a:** WHEN `deploy --help` を表示する場合、ツールは承認を省略する `--auto-approve`(短縮形 `-y`)を一覧に含めなければならない。
- **FR-12-8b:** ツールは `--auto-approve` を `plan` を含む他のサブコマンドへ提供してはならない。
- **FR-12-8c:** ツールは `--confirm` オプションを提供してはならない。IF `--confirm` が指定された場合、ツールは未知オプションとして `CliUsageError`(終了コード 1)としなければならない。旧方式からの移行は [CHANGELOG](../../CHANGELOG.md#1---confirm-の廃止--auto-approve--y-の新設) に記録する。

### FR-13: マルチリージョンデプロイ

1 つのテンプレートを複数のリージョンへデプロイできること。

- 設定ファイルで、テンプレートごとにデプロイ先リージョンを複数指定できなければならない。未指定の場合は既定リージョン 1 つへのデプロイとする。
- リージョンごとのスタックは独立したスタックとして扱い、変更検知・ステート・変更セット・差分表示は(テンプレート × リージョン)単位で管理しなければならない。
- パラメータおよびタグは、共通値に対してリージョンごとの上書きを指定できなければならない(AMI ID や証明書 ARN などリージョン依存の値に対応するため)。タグの優先順位は デフォルトタグ(FR-11) < スタックの共通タグ < リージョン別上書きタグ とする。
- WHEN テンプレートが変更された場合、ツールは設定されたすべての対象リージョンに対して変更セットを作成しなければならない。
- WHEN 設定に対象リージョンが追加された場合、当該リージョンのスタックを `added`(新規作成対象)として扱わなければならない。WHEN 設定から対象リージョンが削除された場合、当該リージョンのスタックを削除対象として扱い、FR-6 の安全装置に従わなければならない。
- 依存関係グラフ(FR-8)はリージョンごとに独立して構築・評価しなければならない(CloudFormation の Export / ImportValue は同一リージョン内でのみ参照可能なため)。リージョン内のデプロイ順序は FR-9 に従い、リージョン間の実行順は設定順の直列とする(並列化は将来拡張)。
- 差分表示・実行ログ・JSON 出力には対象リージョンを明示しなければならない。
- 対象リージョンは FR-7 の許可リージョン設定に含まれていなければならない。IF 含まれないリージョンが指定された場合、fail-closed でエラーとしなければならない。
- インポート(FR-10)はリージョンごとに実行でき、既存のリージョン別スタックを取り込めなければならない。

## 6. 非機能要件

### NFR-1: CI/CD 適合性

- `--auto-approve` により非対話で完結し、進捗・結果を標準出力/標準エラーに構造的に出力すること。
- GitHub Actions からの利用を想定し、差分の JSON 出力・終了コードによる判定・ログの見やすさを備えること。
- 有効な `--output json` の結果は成功・失敗・利用者によるキャンセルを問わず標準出力上の単一 JSON document とし、機械処理を妨げる診断・進捗を混入させないこと。承認要約・承認プロンプト(FR-5-6f)も標準エラーへ分離し、標準出力へ混入させないこと。result 生成前の共通エラー JSON は未装飾の公開用 message のみを使用し、`cause`、stack trace、zod issue 配列、credential、および message 内の stackKey / region / cause 装飾を含めてはならない。

### NFR-2: テスト容易性(TDD 前提)

- AWS API 呼び出しはインターフェースとして抽象化し、モック/スタブによる単体テストが可能な構造とすること。
- 変更検知・依存解析・順序解決などのコアロジックは AWS 接続なしでテストできること。

### NFR-3: 信頼性・冪等性

- 同一状態に対する再実行は安全であること(冪等)。途中失敗後の再実行で、成功済みスタックはスキップまたは「変更なし」となり、失敗地点から継続できること。再実行時には前回実行が残した変更セットを FR-2 に従い検出・回収できること。
- 同一スタックに対する並行操作を検出した場合(`*_IN_PROGRESS` ステータス、ステート世代の不一致)、状態を破壊せず安全に失敗すること。
- `s3` バックエンドのロックと条件付き書き込み(FR-1)により、CI の直列化設定が漏れて並行実行が発生した場合でも、後発の実行はロック取得に失敗して安全に停止し、ステートの正本が破損しないこと。CI 側の直列化(例: GitHub Actions の `concurrency` グループ)は、ロック競合による失敗を待機に変えるための推奨構成としてドキュメント化すること。
- AWS API のスロットリングに対してリトライ(指数バックオフ)を行うこと。

### NFR-4: セキュリティ

- クレデンシャルを保存・出力しないこと。
- `NoEcho` パラメータ等の秘匿値をログ・差分出力・JSON にマスクして表示すること。対象スタックの NoEcho 実効値は、テンプレートの scalar な `Parameters.<name>.Default` を基底とし、設定の明示値で上書きして求め、usecase 境界の共通 redactor で `****` に置換する。この Default 補完は redaction 用の入力だけに適用し、設定オブジェクトおよび復旧比較専用の `inputsHash` 契約を変更してはならない。スタックイベントの `ResourceStatusReason`、スタック/変更セットの `StatusReason`、AWS 例外メッセージ、最終 `errorMessage` を report に格納または逐次通知する前に必ず redactor を通すこと。承認要約(FR-5-6a〜e)へ載せる差分・警告も、承認手段へ渡す前に report と同一の redactor を適用すること。空文字および 4 文字未満の値は誤マスク防止のため置換対象外とする。NoEcho 実効値が予約済み `REQUIRED_PLACEHOLDER`(`__REQUIRED__`)と完全一致する場合は既知の非秘匿 sentinel として置換候補から除外し、必須値不足の診断では `__REQUIRED__` を表示する。部分一致する値や他の NoEcho 実値のマスクは緩和してはならない。コマンド固有 result の warning に例外を変換する場合も、`CfnSyncError.publicMessage` だけを使用し、分類不能な例外は固定の安全な文言へ置換して内部 cause や SDK 生メッセージを含めてはならない。
- ツールの実行に必要な最低限の IAM 権限をドキュメント化すること。

### NFR-5: パフォーマンス

- 数十テンプレート規模のディレクトリで実用的な時間で動作すること。status / graph の変更検知・グラフ構築は CloudFormation / STS API を呼ばずローカルで完結すること。ただし、status で S3 state backend のステートを読み取る API 呼び出しは除く。
- 変更セット待機は先頭ページの状態だけをポーリングし、終端到達時にのみ全ページの差分を取得すること。スタック待機はイベントを 5 秒間隔で取得し、スタック状態取得は 5 秒から最大 15 秒までバックオフすること。

### NFR-6: 保守性

- 機能追加(並列デプロイ、S3 ステートバックエンド、GitHub Actions パッケージング)を想定したモジュール構成とすること。

## 7. 制約条件

- 対象は生の CloudFormation テンプレート(YAML / JSON)とする。テンプレートの変換・生成は行わない。
- CloudFormation がネイティブにサポートする範囲の機能のみを利用する(独自のプロビジョニングロジックを持たない)。
- 1 テンプレートファイル = 1 スタック(リージョンごと)の対応を基本とする。1 つのテンプレートを複数リージョンにデプロイする場合、リージョンごとに独立したスタックとして扱う(FR-13)。

## 8. 将来的な拡張(初期リリースのスコープ外)

- GitHub Actions アクションとしてのパッケージング(差分の PR コメント投稿を含む)
- 独立したスタックの並列デプロイ
- ネスト済みスタック・テンプレートの S3 アップロード対応
