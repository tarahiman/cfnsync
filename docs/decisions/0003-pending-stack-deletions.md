# ADR-0003: リネームで残った旧スタックをステートの削除待ちとして追跡する

- Status: Accepted
- Date: 2026-09-05
- Related requirements: FR-1-16〜FR-1-23 / FR-5-5b7 / FR-5-18e / FR-6-7〜FR-6-12 / FR-11-11 / NFR-3
- Related proposal / issue: [変更提案 0001](../changes/0001-pending-stack-deletions.md) / [Issue #16](https://github.com/tarahiman/cfnsync/issues/16)
- Supersedes: なし
- Superseded by: なし

## Context

FR-1-14 は `stackName` の設定変更を「旧スタック名のスタックの削除 + 新スタック名のスタックの新規作成」として
扱う。`core/detect` は同一スタックキーに `deleted`(旧名)と `added`(新名)の対を生成し、`core/plan` は
create を先、delete を後に並べる。

問題は、`schemaVersion: 2` のステートが 1 スタックキーにつき 1 エントリしか持てないことにある。新名の作成成功を
同じスタックキーへ保存した時点で、旧スタック名の情報はステートから消える。旧名の削除は「同一スタックキーの
create が保存した新エントリを消さない」ために `preserveStateEntry: true` で処理され、削除が未実行・拒否・失敗の
いずれで終わっても、再試行に必要な記録がどこにも残らない。

その結果、`--allow-delete` を指定しない実行、削除保護が有効なスタック、`DeleteStack` や削除後のステート保存が
失敗した実行のいずれでも、旧名スタックが AWS 上に孤児として残り、次回以降の `status` / `plan` / `deploy` では
config と state が揃って新名を指すため `unchanged` となって削除候補に二度と現れない。FR-1 の変更検知、
FR-6 の削除安全装置、NFR-3 の「途中失敗後の再実行で自動収束」に反する。

考慮すべき制約:

- 削除は最も不可逆な操作であり、`--allow-delete`・統合依存グラフの逆順・依存情報を復元できない場合の拒否・
  削除保護・`REVIEW_IN_PROGRESS` 保護・`stackId` 照合という安全装置を一切緩めてはならない(FR-6、§8.3)。
- ステート正本の一貫性は compare-and-swap が担い、fencing はベストエフォートである(§4.5)。追加する記録も
  この位置づけを変えてはならない。
- deploy report の JSON 出力契約(FR-5-16)は、`cancelled` と `reconciliations` 以外のフィールド追加を許さない。
- CREATE 復旧は検証不能入力があるとき fail-closed である(ADR-0002)。復旧経路に依存を増やしたくない。

## Decision

ステートを `schemaVersion: 3` へ上げ、`stacks` とは独立した **削除待ち(pending deletion)** の記録
`pendingDeletions` を持つ。キーは物理スタックを一意に識別する `<スタック名>@<リージョン>`、値は FR-6 の
安全装置が必要とする情報と由来である(FR-1-16)。

リネームで新スタック名の作成成功をステートへ記録する保存操作は、**同一の compare-and-swap ペイロード**で
旧スタック名の削除待ちを記録する(FR-1-18)。削除待ちは、対応する物理スタックが実際に削除された
(または CloudFormation 上に存在しないと確認できた)ときにだけ除去する(FR-1-19 / FR-1-20)。

`detectChanges` は削除待ち 1 件につき `deleted` 分類の対象を 1 件生成し、予約スタックキー
`cfnsync:pending/<スタック名>@<リージョン>` を与える(FR-1-21)。これにより既存の削除経路・安全装置・
削除順序決定・出力契約がそのまま適用され、削除待ち専用の分岐を実行系へ持ち込まない(FR-6-7 / FR-6-8)。
名前空間の衝突を排除するため、`cfnsync:` で始まるテンプレートパスを設定検証で拒否する(FR-11-11)。

v1 / v2 のステートは従来どおり読み込み、削除待ちなしとして補完する(FR-1-17)。

外部から観測可能な振る舞いの定義は要件 ID(上記)と [設計書](../spec/design.md) §4.3 / §4.4 / §5.3 / §7 / §8.3
に置き、本 ADR では繰り返さない。

## Alternatives considered

### A. 旧スタックの削除完了まで新スタックのステート確定を遅延する(不採用)

create 成功後もステートを旧名のまま保ち、旧名の削除が成功した時点で新エントリへ差し替える案。

不採用の理由: **成功した AWS 操作をステートに記録しない**ため、その直後に中断すると「AWS 上に新名スタックが
存在するのにステートは旧名を指す」という別の不整合が生じる。この状態からの復旧は CREATE 復旧(管理タグに
よる由来確認 + 全入力の完全一致)に完全に依存するが、ADR-0002 のとおり `NoEcho` パラメータまたは
`dependsOn` を持つスタックでは fail-closed で拒否され、利用者は手動の秘密値復元を伴う import 手順を
踏まざるを得ない。孤児化した旧スタック 1 件の問題を、より復旧の難しい不整合へ置き換えることになる。
また、遅延している間は新スタックが「未記録のまま実在する」ため、次回実行の create 復旧比較を毎回通す
ことになり、実行のたびに fail-closed で停止するリスクを抱える。

### B. 旧名を `stacks` 内の別スタックキー(合成キー)へ退避する(不採用)

不採用の理由: `stacks` のキーは「テンプレート相対パス@リージョン」という管理単位の定義(§4.1)そのもので
あり、実在しないテンプレートパスを混ぜると変更検知の判定表(設定にあるか / ステートにあるか)が崩れる。
`templateHash` / `inputsHash` / `lastAction` など削除にとって無意味なフィールドへ偽の値を入れる必要も生じ、
`inputsHash` を根拠にした `modified` / `unchanged` の判定へノイズを持ち込む。

### C. 削除待ち専用サブコマンド(`cfnsync prune` 等)を新設する(不採用・将来検討)

不採用の理由: 削除順序は他の管理対象との統合依存グラフに依存するため、結局 `deploy` と同じ計画・承認・実行
経路が必要になる。公開コマンドの重複は FR-5-20a と同じ問題(承認の要否・終了コードの意味・削除プレビューの
解釈の分岐)を招く。

### D. 警告だけを出して追跡しない(不採用)

「旧スタックが残っているかもしれない」旨を 1 回だけ警告する案。不採用の理由: 警告は次回実行で消え、
安全不変条件を「警告して継続」へ緩める典型例である(仕様管理ガイド「安全不変条件の変更」)。

## Consequences

### 利点

- リネーム後に旧スタックが削除されなかった場合でも、以後の `status` / `plan` / `deploy` に削除候補として
  現れ続ける。`--allow-delete` を後から付けた実行で収束する(NFR-3)。
- 削除待ちは既存の削除経路を通るため、安全装置の二重実装がない。
- `DeleteStack` 成功後にステート保存だけが失敗した場合も、次回の Phase A が不在を確認して収束する。
- 「新スタックの作成成功が記録されていない状態で旧スタックだけを削除する」経路(`--on-failure continue` で
  create が失敗した場合)を FR-6-9 で塞げる。

### 欠点、残余リスク、運用上の制約

- **ステート schema が片方向に進む**: `schemaVersion: 3` を保存したステートは旧バージョンの cfnsync では
  `StateCorruptionError` になる。ダウングレードには `s3` のバージョニングまたは `local` の `.bak` からの復元、
  あるいは手動編集が必要である。
- 削除待ちが残っている間、その (リージョン, スタック名) を別のスタックキーが create / update 対象として
  指す構成は fail-closed で拒否される(FR-6-10)。リネームを元に戻す運用は、先に削除待ちを解消する必要がある。
- 削除待ちのリージョンも `allowedRegions` 照合の対象になる。当該リージョンを設定から外すと、削除待ちが
  残っている限り実行が fail-closed で停止する。これは既存の「ステートに残るスタックエントリ」と同じ性質である。
- `DescribeStacks` から `DeleteStack` までの TOCTOU 競合窓は削除待ちでも残る。CloudFormation に条件付き削除が
  ないため原理的に排除できず、`stackId` 照合と fencing で窓を狭めるだけである(§4.5 / §8.3)。それ以上の
  保証は主張しない。
- 削除待ちを利用者が明示的に破棄する手段は提供しない。誤って積み上がった場合はステートの手動編集となる。

### 移行またはロールバックへの影響

- 移行に特別な操作は不要。v1 / v2 のステートはそのまま読め、最初の成功保存で v3 へ正規化される。
- ロールバックは実装の revert に加え、保存済み v3 ステートの復元または手動編集が必要になる。削除待ちを
  失うと Issue #16 の孤児化が再発する。移行手順は
  [CHANGELOG](../../CHANGELOG.md#10-ステート-schema-v3-への移行と削除待ちスタックの追跡) に記録する。
