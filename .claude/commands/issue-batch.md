# Issue バッチ対応

open Issue から**優先度が高く 1 つの PR にまとめられるもの**を選び、実装サブエージェントに対応させ、PR を作り、別のレビューサブエージェントにレビューさせる。

対象指定: `$ARGUMENTS`（Issue 番号の羅列、テーマ語、または空欄。空欄なら自分で選定する）

---

## Step 0. 前提確認

以下を並行して確認する。

- `git status --short` / `git branch --show-current` — 作業ツリーが汚れていないか、今どのブランチにいるか
- 既定ブランチ名を取得して以降 `$BASE` として使う（`main` と決め打ちしない）:
  `git symbolic-ref --short refs/remotes/origin/HEAD | sed 's#^origin/##'`。解決できなければ `git remote show origin` で確認する
- `git fetch origin "$BASE"` — 最新化しておく
- `git log --oneline "origin/$BASE..HEAD"` — 既存の未 push コミットがあるか
- `node_modules` の有無。無ければ `pnpm install --frozen-lockfile`
- `pnpm test` — **ベースラインが緑であること**（件数を記録しておく。実装後の比較基準になる）

ベースラインが赤なら、そこで止めてユーザーに報告する。赤い状態から始めると実装エージェントが既存の失敗を追いかけて迷走する。

## Step 1. Issue の収集と選定

`mcp__github__list_issues`（owner/repo は `git remote -v` から判定、`state: OPEN`）で一覧を取り、候補の本文を `mcp__github__issue_read`（`method: get`）で読む。**タイトルだけで判断しない** — このリポジトリの Issue は本文に実測値・落とし穴・受け入れ条件が書かれており、そこが選定とスコープの根拠になる。

`$ARGUMENTS` に Issue 番号があればそれを対象とし、束ねられるかだけ検証する。空欄なら次の基準で選ぶ。

**優先度（高い順）**
1. 誤った結果を出す / 検証が空振りしているバグ（`bug` ラベル、特に安全不変条件・受入基準の実効性に関わるもの）
2. 壊れているのに CI が気づけないゲートの穴（今後の全変更のリスクを下げる）
3. ユーザー可視の不具合
4. リファクタ・ドキュメント

**1 PR にまとめる基準** — 次のどれかに当てはまるものだけを束ねる。
- **相互依存している**（A を入れると B が無いと CI が赤になる、A を先に入れると B が自動で乗る）
- **同じファイル・同じ層を触る**（別 PR にすると必ずコンフリクトする）
- **1 つのテーマで PR 説明が書ける**（「品質ゲートの堅牢化」のように単一の見出しで説明できる）

逆に、**別の層の独立したバグ**や**大規模リファクタ**は混ぜない。レビュー不能な PR になる。3〜5 件を上限の目安とし、束ねられなかった高優先 Issue は最後の報告でユーザーに挙げる。

選定結果（対象 Issue 番号・束ねる理由・除外した高優先 Issue とその理由）を**実装に入る前にユーザーへ 1 度提示する**。

## Step 2. 作業ブランチの確定

**実装を始める前に必ずここを通す。** 以降の commit / push / PR 作成はすべてここで決めた `$BRANCH` を使い、ブランチ名をその場で書き起こさない。

1. セッションに指定ブランチが与えられている場合（ハーネスが「このブランチで作業せよ」と指示している場合）は、**それが `$BRANCH`**。新しく作らない
2. 指定が無く、いま `$BASE` 以外の作業ブランチにいて、そのブランチが今回の作業のためのものなら、それを `$BRANCH` として使う
3. それ以外（`$BASE` にいる、または無関係なブランチにいる）は、最新の `origin/$BASE` から作る:

```sh
BRANCH="claude/issue-batch-<対象 Issue 番号をハイフン区切り>"   # 例: claude/issue-batch-19-20-21-22
git fetch origin "$BASE"
git checkout -b "$BRANCH" "origin/$BASE"
```

**`$BASE` の上でコミットしない。** `$BASE` は ruleset で直接 push が禁止されているのが通常で、push は拒否される一方**ローカルの `$BASE` にはコミットが残り**、次回以降の作業を汚す。ブランチを作れない事情があるなら、コミットせずユーザーに報告して止まる。

既に同名ブランチが存在する場合は、それが今回の作業の続きかを `git log` で確認する。**対応する PR が既にマージ済みなら、そのブランチに積み増さない** — 同じ名前で `origin/$BASE` から作り直す（`git checkout -B "$BRANCH" "origin/$BASE"`）。マージ済み PR は新しい作業を追跡できない。

## Step 3. 実装サブエージェント

`Agent`（`subagent_type: general-purpose`、`run_in_background: true`）を 1 つ起動する。プロンプトには必ず含める。

- リポジトリパス、**Step 2 で決めた `$BRANCH`**、ベースラインのテスト件数、依存インストール済みであること
- **最初に読むもの**: `CLAUDE.md`、`docs/spec/README.md`、対象 Issue の全文（`mcp__github__issue_read` で自分で取得させる）
- Issue 相互の依存関係と**推奨実装順序**
- Issue ごとの要点（ただし「詳細は Issue 本文が正」と明記する）
- Issue 本文に選択肢がある箇所は、**こちらで結論を出して指示する**（例:「(a) と (b) なら (b) を採る。理由は〜」）。判断をエージェントに丸投げしない
- **Issue の「実測 0 件」等の記述を鵜呑みにせず自分で実行確認させる**。違反が出たらルールを外すのではなく違反箇所を直すのが原則、スコープを大きく超える場合は見送って理由を報告、と指示する
- CLAUDE.md のドキュメント同期ルール（`requirements.md` / `design.md` / `traceability.md` / `tasks.md` / `CHANGELOG.md` の役割分担）に沿って何を更新し何を触らないかを明示
- **完了条件**: `pnpm run quality:check` が緑。加えて Issue の受け入れ条件のうち機械確認できるもの（ネガティブコントロール、`dist/` のバイト一致など）を実際に確認させる
- **制約**: コミットも push もしない（親が行う）／ブランチを切り替えない／テストの `it()` 名・本数を変えない／安全不変条件を弱めない／CLI 出力は英語（NFR-7）
- **報告に含めるもの**: Issue ごとの変更内容（ファイルパス付き）、`quality:check` の実出力要約、受け入れ条件の確認結果、見送った項目と理由、想定外に赤くなった箇所とその対応

起動後、完了通知を待つ間に他の作業（スラッシュコマンドの整備など）を進めてよい。**ポーリングしない**。

## Step 4. 検証・コミット・push・PR

実装エージェントの報告を**そのまま信用しない**。自分で確認する。

1. `git diff --stat` と `git status --short` で変更範囲を把握し、報告と一致するか確認
2. `pnpm run quality:check` を自分で通しで実行して緑を確認
3. テスト件数がベースライン以上で、`it()` 名が変わっていないことを `git diff` で確認
4. コミット。件名は変更全体を表す 1 行、本文に Issue ごとの箇条書きと `Closes #N` を並べる
5. `git push -u origin "$BRANCH"`（Step 2 で決めたブランチ。ネットワーク失敗時のみ 2s / 4s / 8s / 16s のバックオフで最大 4 回リトライ）
6. PR 作成（ready for review）。テンプレート（`.github/pull_request_template.md` 等）があれば見出し構成をなぞる。本文には次を入れる:
   - 対象 Issue と**束ねた理由**（相互依存の説明）
   - Issue ごとの変更内容
   - Issue 本文に選択肢があった箇所で**どちらを選びなぜか**
   - 検証結果（`quality:check`、テスト件数、受け入れ条件の確認）
   - 見送った項目と理由
7. PR 作成後ただちに `subscribe_pr_activity` を呼ぶ

## Step 5. レビューサブエージェント

**実装とは別の** `Agent` を起動し、PR をレビューさせる。プロンプトには必ず含める。

- PR 番号とブランチ、対象 Issue 番号（**Issue 本文を自分で読ませる** — 受け入れ条件との突き合わせがレビューの中心）
- レビュー観点:
  - **受け入れ条件の充足**（Issue のチェックボックスを 1 つずつ潰す）
  - **正しさ**（新しいゲートが空振りしていないか。「設定を足したが実際には何も検査していない」が最も危険な失敗モード）
  - **テストが主張どおりに検証しているか**（このリポジトリで実際に起きた欠陥類型）
  - CLAUDE.md の**安全不変条件**を弱めていないか
  - ドキュメント同期の役割分担（規範文書 / traceability / tasks / CHANGELOG）に違反していないか
  - スコープ逸脱・意図しない挙動変更
- **必ず自分でコマンドを実行して確かめさせる**（`quality:check`、ネガティブコントロールの再現など）。差分を読むだけのレビューにしない
- 指摘は**重大度順**に、根拠（ファイル:行、実行したコマンドと出力）付きで報告させる。指摘が無い場合は「無い」と明言させる
- **制約**: コミットも push もしない、GitHub にコメントを投稿しない（親が判断する）

## Step 6. レビュー指摘の反映

指摘を重大度で仕分ける。

- **修正する**: 受け入れ条件の未達、ゲートの空振り、安全不変条件の後退、明確な誤り → 直して `quality:check` を通し直し、push
- **修正しない**: スコープ外、Issue で明示的に別 issue 送りとされているもの → 理由を明記
- 判断が割れる設計上の指摘 → `AskUserQuestion` でユーザーに聞く

反映後、ユーザーへ最終報告する。

- PR の URL
- 対象 Issue と束ねた理由
- レビュー指摘と、それぞれ直したか / 直さなかった理由
- **束ねられなかった残りの高優先 Issue**（次に何をやるべきかの提示）

---

## 全体を通しての制約

- **`$BASE`（既定ブランチ）の上でコミットしない。** Step 2 で作業ブランチを確定してから実装に入る
- 実装エージェントとレビューエージェントは**必ず別に起動する**。同じエージェントに自分の実装をレビューさせない
- サブエージェントにコミット・push・GitHub への投稿をさせない。外部に出る操作は親が行う
- サブエージェントの報告は**検証すべき主張**であって事実ではない。`quality:check` は自分で通す
- 破壊的な操作（`git reset --hard`、`git stash drop`、ブランチ削除、force push）はユーザーの明示的な指示なしに行わない
